# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a Commodore 64 game called **TITAN Fall** (working title) — a cinematic infiltration puzzle thriller in the vein of *Impossible Mission* and *Paradroid*. The player infiltrates an automated missile launch complex and must subvert its drone workforce to stop a launch countdown. The game is targeted at PAL/NTSC C64 hardware. See `design/gamedesign.md` for the full design document — it is partly out of date but is kept as a source of ideas for future features; this file and `titan.yaml` describe what is actually implemented.

## Build & Run

```
make        # generate world.asm + assemble + pack
make run    # generate, assemble, pack, and launch in Vice
make release # build release/titanfall.d64 (c1541: fresh disk "titan fall", the packed game as TITANFALL)
make sid    # build music/titan_theme.sid — the tune alone as a PSID file for SID players
make clean  # remove game.prg, titanfall.prg, music/titan_theme.prg/.sid and the generated src/world.asm + src/charset.asm
```

The build is four steps handled by the Makefile:
1. **tools/genworld.py** (Python 3 + PyYAML) generates `src/world.asm` from `titan.yaml` — all world data tables (rooms, actors, items, doors, lasers, terminal zones) plus the room map data converted from the vchar64 exports
2. **tools/gencharset.py** generates `src/charset.asm` (`TILE_COLORS` + `CHARSET`) from the vchar64 exports `graphics/titan-charset.s` and `graphics/titan-tile-colors.s`
3. **ACME 0.97** assembles `src/titanfall.asm` → `game.prg` (`-f cbm`, 2-byte load header)
4. **Exomizer** packs `game.prg` + the music PRG (`music/titan_theme.prg`, assembled by ACME from `music/titan_theme.asm`) into a self-extracting `titanfall.prg`

Emulator: **x64sc** (Vice). Do not run `acme` directly; always use `make`.

**`src/world.asm` is generated — never edit it** (it's in `.gitignore` and `make clean` removes it). To change rooms, robots, items, doors, lasers, the starting clock, or the death penalty, edit `titan.yaml` and rebuild. `tools/genworld.py` validates the config (unknown room/item references, >4 robots per room, over-long strings, etc.) and fails the build with a clear message.

### BASIC stub convention

Only `src/titanfall.asm` carries the BASIC stub. The `* = $0801` loader appears once in the whole codebase:

```asm
* = $0801
    !byte $0B, $08      ; next-line pointer
    !byte $0A, $00      ; line number 10
    !byte $9E           ; SYS token
    !pet "2064"         ; decimal address of machine code entry point
    !byte $00           ; end of line
    !byte $00, $00      ; end of BASIC program
; machine code starts here at $0810
```

The SYS address in `!pet` must be kept in sync manually if the header ever changes size.

**Use `!pet` not `!text` for all strings.** `!text` outputs raw ASCII; the C64 uses PETSCII, which has different character codes and causes garbled output.

## Memory Layout

| Address | Purpose |
|---------|---------|
| `$0801` | BASIC stub (SYS 2064) |
| `$0810` | Entry point / code start (code + `TILE_COLORS` must end before `SPRITES_START`, `$2700` today — ~2.8 KB left, see the TILE_COLORS gotcha). Holds `titanfall.asm`'s code + `game.asm` + `TILE_COLORS` |
| `$0340–$0397` | Tape buffer, reused as `SP_BUF` (screen + colour cells under the small search popup) |
| `$0400–$07FF` | Screen RAM (default VIC bank) |
| `$D800–$DBFF` | Colour RAM |
| `$07F8` | Sprite pointer table (end of screen RAM — **must be restored after every CLS call**) |
| `$2700–$37FF` | Sprite frames (`SPRITE_FRAMES` = 68 × 64 bytes, pointers `$9C–$DF`): player 12, robot 12, drone 12, dozer 12, tripod 12, bolt 2, force field 2, cut scene 4 (`CS_FRAMES`, filled at runtime) — packed to end right at `CHARSET`, so the start moves down 64 bytes per added frame — see "Sprites" |
| `$3800–$3FFF` | `CHARSET` — custom 2K room-art charset, the top 2K of VIC bank 0 (see below) |
| `$4000` | `TITLE_SCR`/`TITLE_COL` intro logo (640 bytes), then the generated world data (`src/world.asm`: tables, room maps, wall grids, runtime state arrays), then the CPU-only state modules (`intro`, `gameover`, `win`, `terminal`, `map`, `popup` — code with no VIC constraint, moved up here to free the code area), ending at `HIGH_END` (`$A65F` on 2026-10-10 — past `$A000`!). No VIC constraints here; must stay below `$C000` (an `!error` checks `HIGH_END`). **`$A000–$BFFF` is RAM only because the entry point banks BASIC ROM out (`$01` = `$36`)** — see the gotcha |
| `$C000–$CFFF` | Music `titan_theme` (init `$C000`, play `$C003`, ~1.4 KB; loaded by exomizer) |

## Core Design Constraints

When implementing code, always respect these C64 hardware limits:

- **CPU:** MOS 6510 (6502 derivative); assembler is **ACME** (not cc65, not KickAssembler)
- **VIC-II sprites:** Exactly 8 hardware sprites available — the design intentionally avoids a sprite multiplexer (0 = player, 1, 2, 5, 6 = the room's robots — robot slots 0–3 via `SLOT_HW` —, 3 = the shooter's bolt, 4 = the forcefield robot's field, 7 free)
- **Room layout:** 22 rows × 40 chars (custom charset, screen codes) per room. **The tile — the unit of every coordinate in the game and in `titan.yaml` — is 2×2 chars (16×16 px)**, so a room is 20×11 tiles (X 0–19, Y 0–10); tile (x,y) covers map cols `2x..2x+1`, rows `2y..2y+1`. `bounds:` in `titan.yaml` (→ `ROOM_MAXX/Y`) is optional and defaults to the whole room; the outer walls of the art make the edge tiles solid anyway
- **Memory:** 64 KB total; code, data, and screen RAM must all fit within the standard C64 memory map
- **SID chip:** 3 voices for audio

## State Machine

`GAME_STATE` (`$1A`) holds the current state. The main loop syncs to a raster IRQ at line 50 (~50 Hz PAL); `TICK_FLAG` is set by the IRQ and cleared each frame by `MAIN_LOOP`.

| Value | State | Description |
|-------|-------|-------------|
| 0 | Intro | Title screen, tagline, blinking "press fire" prompt |
| 1 | Game | Playfield with HUD, player sprite, room map, countdown clock, reactor meter |
| 2 | Game over | The clock ran out: red border, the missile room (`MSL_ROOM`, drawn by `DRAW_ROOM`, no sprites) with the clock at `00:00:00` on row 0; after `GO_PAUSE` the missile lifts off (explosion sound as the rumble) and `GO_DRAW` moves it up one char row per step, speeding up (2×(`GO_D0`−k) frames, min 4), through the top wall and off the screen (~3.5 s — `GO_D0` = 13; the rumble is restarted while it flies), leaving the art behind it (`GO_BG`, saved at setup with the missile cells blanked). Then the shared popup box (`DRAW_POPUP_BOX`, "game over / press fire") and fire/any key → intro. The missile is whatever `art.missile_tiles` chars are in the art (all in one room — the build fails otherwise): `genworld.py` emits their bounding box `MSL_X/Y/W/H` and `MSL_CHARS` (the box, 0 = not missile) |
| 3 | Terminal | Terminal menu: this room's robots, view map, logoff (fire next to a terminal; time paused; sprites hidden) |
| 4 | Win | Green border and the "launch aborted. you win! / press fire" popup over the room as it is (sprites off), fire → intro — reached after the explosion when a bolt fired by a player-driven shooter robot enters a win-target tile (the missile room's power cell, `art.win_tiles`), or through a `leads_to: exit` door (none configured now) |
| 5 | Map | Sector map overlay (terminal's "view map" entry; time paused; sprite hidden; fire/any key returns to the terminal) |
| 7 | Explosion | The payoff after the power cell is shot (`SETUP_EXPLODE`/`DO_EXPLODE` in `win.asm`): the cell chars turn dark grey (`PAINT_WIN`), the explosion sound plays, the screen shakes and the border flickers for `EXPL_LEN` = 100 frames (2 s), then the win popup. Time/robots paused |
| 8 | Cut scene | The briefing after the intro's fire press (`cutscene.asm`): the commander (left, green) and the agent (right) as double-size walker sprites, the dialog (`CS_DIALOG`: speaker byte, text lines separated by 1, 0-terminated, `$FF` ends) in speech bubbles above the speaker that close by themselves (50 frames + 2 per character), then the agent walks off to the right and `SETUP_GAME` runs. Fire, Space or Return skip it (straight to `CS_END`). The figures use `CS_FRAMES` (4 frames at the end of the sprite block): copies of walker frames with `%10`/`%11` swapped, made by `SETUP_CUTSCENE`, so the skin comes from `$D026` (light red during the scene) and the clothes from each sprite's own colour. `CS_END` restores `$D017`/`$D01D`/`$D026`/`VIC_SP_MSB`/sprite 0's colour |
| 6 | Popup | "Found item", "door locked" or F2 "where am I" popup (end of a held-fire search that found something, blocked at a locked door, or F2; time/robots paused; a fresh fire/Space press closes it — see the popup section) |

**Stack discipline:** The state machine uses fall-through / `jmp` between states, not `jsr`/`rts`. `MAIN_LOOP` is entered by falling through from init code, never by `jsr`. State transitions use `jmp SETUP_*` not `jsr`, so the return address on the stack is always the one from `DISPATCH`'s `jsr TICK_*`. Never `jsr` into anything that falls into `MAIN_LOOP`.

**Dispatch uses `bne`+`jmp` pairs, not `beq`.** The `DO_*` handlers live in `!source`d files assembled after `CLS`/`RASTER_IRQ`/shared strings, placing them beyond the ±127-byte range of a `beq`. The dispatch reads: `bne MLNOT0 : jmp DO_INTRO` etc.

**State ≠ 1 guard in GAME_ALIVE:** After `READ_KEYS` (so a terminal/popup opened by a key doesn't let `MOVE_PLAYER` take a step behind it) and again after `MOVE_PLAYER`, `GAME_ALIVE` checks `lda GAME_STATE : cmp #1 : bne GAME_TICK_DONE`. This skips sprite update / HUD / status draws whenever any other state (3 terminal, 4 win, 5 map, 6 popup) was entered mid-frame. It used to be `cmp #4 : bcs`, which let the terminal (state 3) through: `UPDATE_ROBOT_SPRITES` then re-enabled the robot sprites right after `SETUP_TERMINAL` had cleared `VIC_SPEN`, so robots stayed visible over the terminal screen.

## Gameplay Architecture

The game has two distinct active modes sharing a single countdown timer:

1. **Human mode** — player explores rooms, scavenges for Access Clearance Chips (levels 1–4) and Direct Override Codes (robot serial numbers)
2. **Robot/proxy mode** — activated at mainframe terminals; the human sprite freezes and the player controls a drone remotely

`PLAYER_MODE` (`$31`) implements this generically: **0 = human control, otherwise (actor index + 1) = that actor is player-driven**. Robots are entries in the generated actor tables (`ACT_*` in `world.asm`); the dozer in room 1 (the puzzle's laser-burner, formerly the splicer) is `ACTOR_BOT3312` (equate from `id: bot3312` in `titan.yaml`).
- Selecting a robot in the terminal (`TERM_ROBOT` in `terminal.asm`) sets `PLAYER_MODE=actor+1`, redraws the room and shows the link popup (`SETUP_LINKED` in `popup.asm`: "you are now controlling" / the robot's name, centred — generated `ACT_LNAME_n` rows via `ACT_LNAME_LO/HI` — / "for 30 seconds. f7 aborts.", the seconds from `CFG_LINK_S`); the link timer only starts once fire closes it (state 6 pauses `DO_GAME`) — unless `TERM_LINK` refuses: the robot is destroyed (`TMSG_DEAD`), `locked: true` in `titan.yaml` (`ACT_LOCK`, `TMSG_LCK`), or needs a security code the player has none of (`CODE_MSG_n`, e.g. "access denied. no security code a."). Otherwise it spends that code and calls `START_LINK`. See "Security codes" and "Terminal menu".
- While `PLAYER_MODE≠0`, `MOVE_PLAYER` (`game.asm`) dispatches to `MOVE_ACTOR`, which moves `ACT_X/Y` of actor `PLAYER_MODE-1` — WASD/joystick drive the robot, clamped to its own room's `ROOM_MAXX/Y` bounds; no doorway checks (robots can't leave their room); the human sprite stays frozen at its last `PLR_X/Y`. Driving into an active laser destroys both robot and laser — see "Lasers can be destroyed by a driven robot".
- `TICK_ROBOT` skips the AI step (idle and attack) for the player-driven actor (index+1 == `PLAYER_MODE`) so the AI doesn't fight manual control.
- `CHECK_SPRITE_HIT` ignores player-sprite collisions while `PLAYER_MODE≠0` (the human is standing safely at the terminal); it still reads `VIC_SPCOLL` every frame regardless of mode so the hardware latch doesn't accumulate a stale hit for when control returns to human.
- **A link expires — there's no other way to end it.** `START_LINK` (`game.asm`, from `TERM_ROBOT`) sets `PLAYER_MODE` and `LINK_S = CFG_LINK_S` (`game.robot_link_seconds` in `titan.yaml`, default 30, 1–99). `TICK_LINK` (from `GAME_ALIVE`, right after `TICK_CLOCK`) counts it down in game frames (`LINK_JIF`, 50 per second), so it pauses with the clock in terminal/map/popup. At 0 it falls into `END_LINK`: `PLAYER_MODE=0` and control reverts to the human, with a cyan border flash (`BFLASH`, 15 frames — cyan like the HUD's "human"). **F7 ends a link early**: `READ_KEYS` (`RKPROXY`) scans F7 (held, no edge detect needed) while driving and `jmp`s to the same `END_LINK` — but not while the robot is dying in a laser (`ACT_ALIVE`=2; `ROBOT_LASER_DEATH` ends the link itself). (Burning out a laser still ends the link at once, and `RESET_ROUND` clears it.) Fire and the old X key don't end a link. **Robots can't use terminals or search**: both fire/Space actions are gated on `PLAYER_MODE=0`. While driving, fire (`KEY_SPC`) shoots instead — but only if the driven robot has `attack: shoot` (`RKPROXY` in `READ_KEYS` → `FIRE_BOLT` in its facing direction, `BOLT_PLR=1`); otherwise it does nothing — and the frozen human still standing in the terminal zone can't re-trigger the terminal.
- `DRAW_HUD_DYNAMIC` and the F2 popup (`SETUP_WHERE`) both branch on `PLAYER_MODE` to show "robot"/`ACT_X/Y` instead of "human"/`PLR_X/Y`. The HUD shows the link's seconds left after it — "robot 30", "robot 29", … (`LINK_S` at cols 6–7, cleared in human mode).

Key state to track:
- Countdown timer (real-time; configurable penalty and respawn per human death, see "Death & Respawn"; Game Over only when the clock hits zero)
- Inventory: `ITEM_STATE` array (0=hidden 1=carried 2=used — a key that opened its door), one byte per config item
- Per-actor: `ACT_X/Y` (tile position), `ACT_TGT` (patrol waypoint, or a roaming robot's current leg), `ACT_ALIVE` (0=destroyed 1=alive 2=dying — sliding into a laser), `ACT_DIR`/`ACT_ANIM` (facing, walk frame), `GL_PXL/PXH/PY` (glided sprite pixel position)
- Per-laser: `LASER_STATE` (0=active 1=destroyed)
- Active mode (human / drone) and which actor is linked (`PLAYER_MODE`)

Movement is fully table-driven (`MOVE_PLAYER`/`TRY_MOVE` in `game.asm`):
- **Bounds:** each room has its own `ROOM_MAXX`/`ROOM_MAXY` (default and maximum 19/10, the full 20×11-tile room; walls in the art do the real limiting).
- **Doors** (`DOOR_*` tables) are rectangles *one tile outside* the walkable range (e.g. `x: -1` on a left wall, `y: 10` on a bottom wall, encoded `$FF`/`$0A`). A move landing inside a door rect triggers it: keyed doors first (`DOOR_KEY` = item index+1, 0=none) — without the key the locked popup (acts like a wall); with it, the first push **opens** the door (see "Keyed doors open" below) and the player stays put; once open (`DOOR_OPEN`) it's an ordinary door — then either the win screen (`DOOR_DEST=$FF`, `leads_to: exit`) or a room change (`DOOR_AX/AY` set the arrival position; `$FF` = keep current coordinate). Anything out of bounds that isn't a door is a wall.
- **Keyed doors open.** A door with a `key:` is drawn closed in the art with `art.door_tiles` chars (`$A3` in a top/bottom wall, `$B0` in a side wall) in the room's edge rows/columns at the door. `genworld.py` (`door_art_patches`) lists those cells — the 2 char rows/columns at that wall, along the door's span ±1 char — as `DOOR_ART_n` (via `DOOR_ART_LO/HI`, same format as the laser patches; empty for keyless doors; a warning if a keyed door has no door art). When the player walks into it carrying the key, `DOOR_ENTER` sets `DOOR_OPEN` (runtime, one byte per door), `ERASE_DOOR` repaints them as `floor_tile` (shares `ERASE_ART` with `ERASE_LASER`), the border flashes green, and **the key is used up** (`ITEM_STATE=2`, so it leaves the status line's card slot and can't open another door); the player doesn't move that push, so the opening is seen, and the next push goes through. `DRAW_ROOM` re-erases every open door in `CUR_ROOM` (like destroyed lasers). `DOOR_OPEN` is reset only by `SETUP_GAME` — an opened door stays open across a death. **Closed doors are solid.** `genworld.py` makes every tile with `art.door_tiles` chars solid. A keyed door's tiles (from its art patches, unless they're wall anyway) also carry the door's **keyed-door number** + 1 (its position among the keyed doors in `titan.yaml` order — `DOOR_KNUM` (door → number + 1, 0 = no key) and `KEYDOOR` (number → door index); at most 15 keyed doors, anywhere in the file) in bits 4–7 of their `ROOM_WALLS_n` byte (`=` in the comment pictures): `TRY_MOVE` sends a push into one to `DOOR_ENTER` (locked popup, or open it), and opening runs `OPEN_DOOR_WALLS`, which clears those tiles' solid bit in RAM; `RESET_WALLS` (`SETUP_GAME`) sets it again (and clears every tile's searched bit 3). The placement checks treat keyed door tiles as open (door arrivals land on them). Door art that belongs to no keyed door is plain wall — room 5's EXIT is such a decoy on purpose: it's how the agent got in, it never opens, and the only way out is stopping the missile (don't give it a door entry). Robots are blocked by closed doors and can't open them.
- **Interior walls** come from the room art, computed at build time: `genworld.py`'s `wall_grid` marks a tile solid if any of its 2×2 map chars (map cols `2x..2x+1`, rows `2y..2y+1` — where the sprite's feet stand) is in `art.solid_tiles` in `titan.yaml` (`$84–$8B`, the wall glyphs, `$A4`, the missile bay's "keep out" border, and `$A6`, the power cell; crates, `art.crate_tiles`, are solid too, see "Movable crates"). It emits `ROOM_WALLS_n` (20 bytes per tile row, index `y*20+x` — max 219, so one byte index covers the room; bit 0 = solid, bit 1 = win target (always solid too — bit 1 *without* bit 0 is a pit, see "Pits"), bit 2 = searchable (not plain floor), bit 3 = searched (runtime, set by `SEARCH_TICK`), bits 4–7 = keyed-door number + 1 (`KEYDOOR`/`DOOR_KNUM`) — `WALL_AT` returns bit 0 as carry and the rest shifted down in A, with an ASCII picture of the grid in the comments) via `ROOM_WALL_LO/HI`; `WALL_AT` (A = room) looks a tile up, and both `TRY_MOVE` (human) and `TRY_ACT` (driven robot) treat a solid tile like a wall before checking lasers. The build **fails** if a player start, a robot start or any tile on a patrol path, an item, or a door arrival lands on a solid tile (or a terminal zone is all wall) — so new art and the config can't silently drift apart for walls. Furniture isn't solid unless its codes are added to `solid_tiles`.
- **Pits** (`art.pit_tiles`, `$AC`): a tile with any pit char (and no wall char) is a pit, encoded as bit 1 without bit 0 in `ROOM_WALLS_n` (`O` in the comment pictures) — which is why `genworld.py` requires every win-target tile to be solid. `WALL_AT` returns carry set for a pit (so robots — driven, roaming, rushing — and line of sight treat it as a wall, for free) **plus N set** (A bit 7). Only two callers look at N: `TRY_MOVE` (the human steps in with `PLR_DYING=2`; `UPDATE_SPRITE0` hides sprite 0 once the glide arrives and calls `PLAYER_DIE` — the usual death; `RESET_ROUND` re-enables the sprite) and `BOLT_TICK` (bolts fly over pits — checked before the win-target test, since a pit's A bit 0 reads like a target). Starts, patrols, items and door arrivals on a pit fail the build.
- **Gates and pressure plates** (`src/plates.asm`; `art.gate_tiles` = `$B2`, `art.plate_tiles` = `$B1`). All gate chars of a room are its one gate (`GATE_ROOM/X/Y` tiles, art cells `ROOM_GATEART_n`), solid at start; plate tiles (`PLATE_ROOM/X/Y`) are walkable and **not searchable** (so `CR_FREE` lets a crate onto one). Runtime `GATE_STATE` per room: 0 closed, 1 held open, 2 latched open. `PLATE_TICK` (every game frame, `GAME_ALIVE`): in a room with plates, when every plate is loaded (`LOADED_AT`: the human, a robot, or a crate/mirror on it) the gate opens (state 1, green flash: `GATE_OPEN` clears the solid bits via `GATE_SOLID`, `GATE_PAINT` paints the cells floor); when one is emptied it closes again (`GATE_CLOSE`: solid, the map's chars back via `ART_LIST`) unless something stands in it (`GATE_OCCUPIED`); **the human stepping onto an open gate tile latches it (2)** — so leaving and re-entering can't trap them behind it. A target hit latches too. `GATE_ROOMRESET` (end of `CRATE_RESET`, i.e. `RESET_ROOM`) turns 1 back to 0 in reset rooms; 2 survives everything but `GATE_RESET` (`SETUP_GAME`, which also makes every gate/target tile solid again). `GATE_PAINT` is part of `ROOM_OVERLAYS` (crates, filled pits, open gate, destroyed target), which every "put the map's chars back" path calls afterwards (trap beam off, laser beam erase). Validation: plates need a gate in the room.
- **Emitters and mirrors** (`src/beam.asm`; `art.emitter_tiles` = `$B3` in an outer wall — fires into the room, direction from the wall it's in (`EMIT_ROOM/X/Y/DIR`, one per room), `art.target_tiles` = `$B8` (`TGT_ROOM/X/Y`, art `ROOM_TGTART_n`, solid), `art.beam_h_tile` = `$B4` (horizontal beam; vertical is `$81`), `art.mirrors: {slash, backslash}` = the 4 chars of a `/` / `\` mirror tile). Mirrors are movable objects like crates (`CRATE_KIND` 1/2; see "Movable crates"). `BEAM_UPDATE` erases the drawn path (map chars back + `ROOM_OVERLAYS`), then traces from the emitter tile by tile: floor and pits pass; a mirror turns it (`TURN_SLASH`/`TURN_BACK`); the room's target, if intact, is destroyed (`GATE_OPEN` with 2, `TGT_SOLID` clears its solid bits, its art painted floor, zap + green flash) and the trace restarts through it; any other solid tile stops it. Up to `BEAM_MAX` = 64 tiles (`BEAM_X/Y/AX`), drawn as `$81` in the tile's left char column (vertical) or `$B4` in its top char row (horizontal); `ANIM_LASER` flips `$B4`'s dash rows too. It runs from `DRAW_ROOM` (`ROOM_DYNAMIC`, which also does the trap beam) and after every crate/mirror push (`CRATE_PUSH`). **The beam kills**: the human stepping in (`TRY_MOVE` → `BEAM_AT`, `PLR_DYING` like a laser), the human standing where a push sends it, and robots (`BEAM_ZAP`, every frame, like `TRAP_ZAP`) — a dozer pushing a mirror must not end up in the new path. Validation: an emitter needs a target in the room; stray mirror chars fail the build.
- **Movable crates** (`src/crates.asm`, `art.crate_tiles` = `$AB`/`$AD`, the left/right halves). `genworld.py` (`find_crates`) makes every tile whose 2×2 chars are *all* crate chars a movable crate, and every tile drawn exactly like an `art.mirrors` pattern a mirror (`NUM_CRATES`, `CRATE_ROOM/SX/SY`, `CRATE_KIND` 0 crate / 1 `/` / 2 `\`; `CRATE_CH` = 4 chars TL/TR/BL/BR per kind — all crates must look the same, the build fails otherwise); crate chars not on a whole tile stay fixed walls and the build **warns** with their map cells (room 7's bottom-left stacks at cols 1–2 and 9–10 today). Movable crates are taken out of `ROOM_MAP_n` (floor there) and their start tiles are solid + searchable (bits 0 and 2) in `ROOM_WALLS_n`; at runtime `CRATE_X/Y` (pre-set to the start tiles in `world.asm`, so the first reset doesn't clear tile (0,0)) say where each one is, and a push moves those two bits with it — so walking, robots, sight and bolts all see a crate as a wall wherever it is. `DRAW_ROOM` calls `CRATE_DRAW_ALL`; `RESET_ROUND` calls `CRATE_RESET` (two passes: every reset crate off the grid, then back on at its start), so a death resets the room's crates — the way out of a Sokoban dead end (two crates side by side against a wall can't be separated). **Pushing:** an actor type with `push: true` (`TYPE_PUSH`; the dozer) that is player-driven into a crate (`TRY_ACT` → `CRATE_PUSH`) pushes it one tile on, to tile + (crate − robot), if that tile is in bounds, plain floor (wall byte 0 apart from the searched bit — no wall, crate, pit, furniture/item, door), not an active laser and nobody (robot or the human) stands on it (`CR_FREE`); the crate jumps and the robot glides into its old tile. `CRATE_PAINT` (A = mode) repaints a tile with `TILE_COLORS`: 0 = the room map's own chars (where a crate left — floor, or a plate it stood on), 1 = floor (a filled pit), 4 + kind×4 = a crate/mirror. After a push `CRATE_PUSH` calls `BEAM_UPDATE` (retrace + `ROOM_OVERLAYS`). **A crate pushed onto a pit fills it** (`CR_FREE` also accepts a pit tile — wall byte bit 1 alone, ignoring searchable/searched — and sets `CR_PIT`; `CR_FILL`): the crate leaves the game (`CRATE_X` = `$FF`, skipped everywhere), the pit tile's wall byte becomes 0 (plain floor — the player and robots can walk on it) and it's painted with floor chars. `genworld.py` lists every pit tile (`NUM_PITS`, `PIT_ROOM/X/Y`, `PIT_WB` = its original wall byte); runtime `PIT_FILLED` marks the filled ones, which `CRATE_DRAW_ALL` paints as floor on every redraw (the map data still has the pit) and `CRATE_RESET` turns back into pits (between its two crate passes) — so a death or leaving the unfinished room brings back both the pit and the crate. In room 7, crate (10,7) pushed left three times fills the pit at (7,7).
- **Laser traps** (`src/traps.asm`, `art.trap_tiles` = `$AE`, also in `solid_tiles` — it sits in a wall). `genworld.py` lists every trap char (`NUM_TRAPS`, `TRAP_ROOM`, `TRAP_X` = its tile column, `TRAP_Y0` = the first tile row below it, `TRAP_ROW1`/`TRAP_COL` = map row/column of the first beam char; a warning if a wall sits right below it) and `CFG_BEAM` = `art.laser_tiles[0]` (`$81`). Traps fire **down** only (the beam glyph is vertical). **While the human stands on any tile in a trap's column (at or below `TRAP_Y0`) its beam is on**, from under the trap down to the first tile row that is solid and not a pit (`TRAP_REACH`, `WALL_AT`: C set, N clear — re-evaluated on every step, so a crate pushed out of the line lengthens it; a pit doesn't stop it). Stepping onto a tile the beam reaches kills (`PLR_DYING=1`, the laser death on arrival); behind the blocker the beam shows but is harmless. Stepping out of the column switches it off. `TRAP_SHOW` does the on/off/redraw (from `TRAP_CHECK` on every committed human step, `TMCOMMIT`, and from `DRAW_ROOM`, which first clears `TRAP_ON` — so after a popup/terminal/respawn redraw the beam is back if the player is still in the column); `TRAP_ON` (trap + 1) / `TRAP_LEN` (its reach) remember what's on screen. `TRAP_ROWS` draws the beam or puts the room map's chars back (`ROOM_MAP_n`, so a destroyed laser crossing the column would reappear — none does today), then `TRAP_OFF` calls `CRATE_DRAW_ALL` so crates/filled pits show over the restored cells. **The beam kills robots too** (like room 1's laser): `TRAP_ZAP` (every game frame from `GAME_ALIVE`, after `MOVE_PLAYER`) destroys any living robot (`ACT_ALIVE=1`) in `CUR_ROOM` whose tile the beam on screen reaches (`TRAP_ON`; its column, `TRAP_Y0` .. `TRAP_LEN`−1) — `ACT_ALIVE=0`, zap sound, yellow border flash, and a driven one hands control back (`PLAYER_MODE=0`). Unlike room 1's laser the trap isn't burnt out by it. So the player waits behind the blocker with the beam on and lets a roaming robot walk into it (room 6's tripod). A destroyed robot comes back with a room reset (death, or leaving room 6 before its goal is done). Room 6: the trap at map col 16 in the top wall covers tile column 8 down to the crate at (8,7) — cross that column below the crate.
- **Lasers** (`LASER_*` tables) are rectangles inside the room; `LASER_AT` checks the attempted position against every active laser in the current room. The human steps onto the tile but is already dying (`PLR_DYING=1`: `MOVE_PLAYER` ignores input) and `UPDATE_SPRITE0` calls `PLAYER_DIE` once the sprite has glided onto the beam — the same "finish the slide, then die" as a driven robot; a player-driven robot enters the tile and `ROBOT_LASER_DEATH` destroys both robot and laser.

Doorway transitions call `DRAW_ROOM`, which blits 22×40 chars via the `ROOM_MAP_LO/HI` pointer tables and then calls `ASSIGN_SPRITES` to remap the new room's actors onto the robot sprites (1, 2, 5, 6).

### Adding content (config-only recipes)

- **New room:** author the art in vchar64 (22×40, shared charset — see `graphics/README.txt`), export the map as ASM, add a `rooms:` entry in `titan.yaml` (name, `vchar64_map`, `player_start`; `label` — its name on the sector map — and `bounds` optional) plus doors linking it to its neighbours (a door in each direction of travel, one per room). The sector map updates itself (see "Sector map").
- **Room goal (orders line):** `goal: {text: ..., done: {found: <item> | opened: <room> | visited: <room>}}` in the room's entry.
- **New hidden item:** add an entry under `items:` (label ≤12 chars, found_text ≤30 chars) and place it with a `things:` entry in a room, on a tile with something drawn on it (not plain floor — the build checks). Lock any door with `key: <item>`.
- **New hidden security code:** an `items:` entry with `code: <letter>` (found_text and label optional — they default to "security code <letter> found!" and "code <letter>"; the label is never shown) plus a `things:` placement — finding it adds one to that code's count. **New code type:** one more line under `security_codes:` (at most 3).
- **New robot:** add a `robots:` entry in a room (`type`, `start`, a two-point `patrol` if it patrols — none for `idle: roam` —, optional `idle:`/`attack:` to override its type's behaviour, **required `code:`** — the security code a terminal link costs, a letter from `security_codes:` or `none` — optional terminal `name:` ≤22 chars and `locked: true`; ≤4 robots per room). It appears in the terminal menu of its room automatically. Give it an `id:` if code needs to reference it (emitted as `ACTOR_<ID>`). A new *type* needs an `actor_types:` entry, a sprite data block in `titanfall.asm` (64-byte aligned, referenced by label), and its behaviour: `idle:` (`patrol` or `roam`; default `patrol`) and `attack:` (`none`, `rush`, `shoot` or `forcefield`; default `none`), both per type with a per-robot override. An `idle: roam` robot takes no `patrol:` (the build rejects one); the old `ai:` key is rejected with a pointer to the two new ones.
- **New laser:** one line under the room's `lasers:`.
- **New terminal:** just draw it in the room art (chars `$8C`–`$8F`, `art.terminal_tiles`). `genworld.py` finds every 4-connected group of terminal chars (`find_terminals`) and makes it a terminal zone (`TERMZ_*`): the tiles under the group plus one tile around them, clipped to the room — so a terminal works from any side. A room's old `terminals:` key is rejected, and an item inside a terminal zone fails the build (fire there opens the terminal, so the item could never be searched for).
- Check the room art visually matches the config rectangles — only walls are validated against the art (placements inside walls fail the build); lasers/doors/terminals are not.

Every sprite file in `src/` is now `!source`d. Adding a set means bumping `SPRITE_FRAMES`, and each frame takes 64 bytes from the code area since the block grows downward. All sets use the same shared MC0/MC1 colours, with `%10` as the per-sprite colour. `src/c64_spritemate.spm` is the Spritemate project they're edited in.

The files are `!source`d back-to-back into one block that ends exactly at `CHARSET` (`* = CHARSET - SPRITE_FRAMES*64` in `titanfall.asm`; ACME can't set `*` from a forward reference, so **`SPRITE_FRAMES` must be updated by hand when a set is added or removed** — an `!error` fails the build if it doesn't match) — each frame is 64 bytes, so they stay 64-byte aligned as long as every file holds whole frames. **Commenting frames in or out shifts everything after them**; that's fine because everything addresses frames by label (`sprite:` in `titan.yaml`, `SPRP_*` equates), never by hard-coded pointer value.

**Frame selection** (`FRAME_PTR` in `game.asm`): pointer = `TYPE_SPRPTR + (facing − TYPE_DIR0)*3 + frame`. Per actor type in `titan.yaml`:
- `sprite:` — label of the type's first frame
- `directions: 4` (default; facings `DIR_DOWN/UP/LEFT/RIGHT` = 0–3) or `2` (left/right only → `TYPE_DIR0=2`; `ACT_FACE` ignores up/down, so the actor keeps its last horizontal facing while moving vertically). All current types use 4 — robots need up/down poses because a robot taken over at the terminal can be driven in every direction; `directions: 2` is only for a future type with a left/right-only sprite set.
- `anim: walk` (default — frame advances rest→walk1→walk2→walk1… once per tile step, back to rest when a step doesn't happen: idle player, patrol waypoint pause) or `hover` (ignores steps; loops hover/move1/hover/move2 off the free-running `ANIM_CNT`, 8 frames per pose)

State: player `PLR_DIR`/`PLR_ANIM` (zero page); actors `ACT_DIR`/`ACT_ANIM` (runtime arrays in `world.asm`, reset by `RESET_ROUND`). The facing is set on every move *attempt* (so walking into a wall turns you), the walk frame only on a committed step (incl. walking through a door). `UPDATE_SPRITE0` / `UPDATE_ROBOT_SPRITES` write the frame pointer into `$07F8–$07FA` every frame; `ASSIGN_SPRITES` sets each slot's colour (and an initial pointer) on room entry. `ATYPE_<NAME>` constants (e.g. `ATYPE_HUMAN`) are emitted by `genworld.py`.

After every `CLS` the pointers are reset to `SPRP_PLAYER`/`SPRP_ROBOT`/`SPRP_DRONE` (just sane defaults — the per-frame update replaces them). `VIC_SPEN` is set to `$07` during game state (`UPDATE_ROBOT_SPRITES` clears the bits of unused/dead/off-room slots every frame; `BOLT_TICK` and `FIELD_TICK` set/clear bits 3 and 4 every frame), `$00` in all other states.

### Actors and robot AI (idle + attack)
All robots are rows in the generated `ACT_*` tables (the player is *not* in them; `PLAYER_MODE` maps "actor index+1" onto them for proxy mode). Static data per actor: `ACT_TYPE` (indexes `TYPE_SPRPTR`/`TYPE_COLOR`), `ACT_ROOM`, `ACT_SX/SY` (start), `ACT_WX0/WY0`/`ACT_WX1/WY1` (two patrol waypoints; both = the start for a roaming robot), `ACT_IDLE`/`ACT_ATTACK` (behaviour, below), `ACT_LOCK`, `ACT_CODE`. Runtime state: `ACT_X/Y`, `ACT_TGT` (which waypoint it's heading for; a roaming robot's leg), `ACT_ALIVE`, `ACT_DIR/ANIM/FAST`.

`TICK_ROBOT` is called every game frame. Its timer `ROB_TMR` fires every `ROB_HALF` = 8 frames and flips `ROB_PHASE` (`$3D`); a normal-pace actor acts only on phase 0 (every `ROB_PERIOD` = 16 frames), a rushing one (`ACT_FAST=1`) on every half period. For each alive, non-player-driven actor it runs `ACTOR_THINK`. A robot's behaviour has two independent parts, both set per type in `titan.yaml` with a per-robot override: **`attack:`** (`ACT_ATTACK`, `ATK_NONE/RUSH/SHOOT/FORCEFIELD` from `genworld.py`'s `ATTACK_NAMES`) is what it does while `SEES_PLAYER`, **`idle:`** (`ACT_IDLE`, `IDLE_PATROL/ROAM` from `IDLE_NAMES`) what it does otherwise. `ACTOR_THINK` dispatches on the attack (`ATK_NONE` goes straight to idling); each attack handler (`RUSH_THINK`, `SHOOTER_THINK`, `FIELD_THINK`) tests `SEES_PLAYER` and falls back to `ACTOR_IDLE`, which dispatches on the idle. Any combination works. `SEES_PLAYER`: human mode (in proxy mode the frozen human isn't attacked), not dying, same room, **same tile row**, no wall tile between them via `WALL_AT`; lasers don't block sight.

Idle behaviours:
- **`idle: patrol`** (all robots except room 2's drone) — `ACTOR_PATROL_STEP`: one step toward the current target waypoint (X axis first, then Y; on arrival the target flips). Actors in other rooms keep patrolling off-screen. Every step goes through `ROAM_TRY` (bounds, walls — crates included —, active lasers): a robot walking back after a terminal link, or one whose path a pushed crate blocks, tries the other axis and otherwise waits (it used to walk straight through walls). No `patrol:` (both waypoints equal) = stand still — at the start, or wherever a link left it (a respawn in the room puts it back). A patrolling robot with `attack: rush` or `forcefield` walks back to its patrol X-first after the attack, so `genworld.py` **requires its patrol to be horizontal through its start** (both waypoints on the start row): attack and return then only cover tiles of that row that the line-of-sight test found free of walls.
- **`idle: roam`** (room 2's drone, room 6's tripod) — a random walk over the whole room instead of a waypoint shuttle: `ROAM_STEP` walks a leg — a random direction (`DIR_*`) for `ROAM_MIN`..`ROAM_MIN`+7 = 2–9 tiles — then picks a new one. When the next tile is blocked (outside `ROOM_MAXX/Y` of the actor's own room, a solid tile via `WALL_AT`, an active laser via `LASER_AT_A`, which takes the room in A and so also works off-screen) it picks a new leg, trying the four directions starting from a random one, and stands still that tick if all four are blocked (`ROAM_TRY` does the test and the step). The leg lives in `ACT_TGT` (steps left × 4 + direction — a roaming robot has no waypoints, and `RESET_ROUND`'s `ACT_TGT=1` reads as "no steps left", so it picks a leg on its first tick); the direction can't live in `ACT_DIR`, which `ACT_FACE` doesn't update for up/down on a 2-direction type. It needs no horizontal-patrol rule with any attack: rush/forcefield only walk tiles of its row that `SEES_PLAYER` found free of walls, and after losing sight it just roams on from wherever it is. Randomness comes from `RAND` (`game.asm`): the `LFSR_ST` LFSR stepped once and XORed with CIA1 timer A low byte (`CIA1_TALO`, `$DC04` — the KERNAL's ~60 Hz jiffy timer keeps counting with its IRQ disabled, and drifts against the 50 Hz frame; the LFSR alone gave too-similar successive picks, the drone walked up and down one column). Only bits 3–7 are used (the `$B8` feedback never reaches the low 3 bits). `RESET_ROUND` seeds `LFSR_ST` from the same timer (`ora #1`, never 0), so the walk differs per game.

Attack behaviours (while `SEES_PLAYER`):
- **`attack: rush`** (room 2's drone, room 6's tripod) — `RUSH_THINK`: while `SEES_PLAYER` it `HUNT_RUSH`es: `ACT_FAST=1` and one step along the row toward the player every half period, at double speed — the player's own pace — and glides at `GL_FAST` (`UPD_SLOT` checks `ACT_FAST`). It never steps into an active laser (`LASER_AT`); it stops and waits at the beam instead. The sprite collision does the killing. Losing sight clears `ACT_FAST`, and it goes back to idling at normal pace. Speed only changes when a glide has finished: a normal-pace actor is only asked on phase 0, and a rusher that loses sight on phase 1 waits for phase 0 before its first slow step — otherwise the 1 px/frame glide would lag a tile behind. `RESET_ROUND` clears `ACT_FAST` and `ROB_PHASE`.
- **`attack: forcefield`** (room 3's tripod) — `FIELD_THINK`, at normal pace: while `SEES_PLAYER` it raises its force field (`FIELD_ACT` = actor+1, zero page `$49`) and steps along the row toward the player at **normal** pace (`ADVANCE`, the step shared with `HUNT_RUSH` but without `ACT_FAST`; never into an active laser). `FIELD_TICK` (every game frame, before `BOLT_TICK`/`CHECK_SPRITE_HIT`) draws the field on **hardware sprite 4** — `forcefield_1/2` alternating every 2 frames, in the robot's `TYPE_COLOR` — `FIELD_OFS` = 20 px ahead of the robot's glided sprite on the side it faces (so it slides with the robot), and hides it when there's no field or the owner is dead, driven, in another room or facing up/down. Touching the robot or the field is the ordinary sprite-collision death. Losing sight clears `FIELD_ACT` and it goes back to idling; `DRAW_ROOM` clears it too. One field at a time (a second forcefield robot that sees the player takes it over).
- **`attack: shoot`** (room 1's sentry, room 4's guard, room 5's sentry) — `SHOOTER_THINK`, at normal pace: while `SEES_PLAYER` it stops, faces the player and fires a bolt along the row (`FIRE_BOLT`, `BOLT_PLR=0`) unless one is already in flight. **A player-driven shooter fires too** — fire shoots in its facing direction, any of the four. There is **one bolt** for everyone (zero page `BOLT_ON/DIR/XL/XH/Y/PLR`, `$3E–$43`; `BOLT_DIR` is a `DIR_*`), drawn on **hardware sprite 3** (`bolt_1/bolt_2` from `src/c64_bolt_sprites.asm`, `SPRP_BOLT`, white via `VIC_SPCOL3`, multicolour). `BOLT_TICK` (every game frame, after `UPDATE_ROBOT_SPRITES`, before `CHECK_SPRITE_HIT`) moves it `BOLT_SPEED` = 3 px/frame. `BOLT_XL/XH` and `BOLT_Y` are the bolt centre in room pixels (`tile*16+8`; X is 9 bits; sprite X = X + 12, MSB bit 3; sprite Y = Y + 54, i.e. a robot's sprite Y on that row). It vanishes when its centre's tile is a wall (`WALL_AT`) or off the room. **Winning:** `WALL_AT` also returns the tile's win-target bit; a bolt with `BOLT_PLR=1` entering a target tile `jmp`s to `SETUP_EXPLODE` (state 7, see below) (`GAME_ALIVE` checks the state right after `BOLT_TICK`). Target tiles are the tiles with any `art.win_tiles` char (`$A6`, the missile room's power cell — tiles x 1–3, y 4–6), bit 1 of `ROOM_WALLS_n` (`*` in the comment pictures). The power cell is also in `solid_tiles` (you can't walk onto it; those tiles are `3` = solid + target), so `BOLT_TICK` tests the target bit **before** the solid bit — otherwise the player's bolt would just die on it. AI bolts (`BOLT_PLR=0`) die on it like on any wall. **The intact cell flickers cyan/purple:** `genworld.py` emits per room the map offsets of every `win_tiles` char (`ROOM_WINART_n` via `ROOM_WINART_LO/HI`; empty in rooms without one); `PAINT_WIN` (A = colour) recolours them, `WIN_FLICKER` picks cyan/purple from `ANIM_CNT` bit 4 and is called every 16 game frames from `GAME_ALIVE` and at the end of `DRAW_ROOM` (so a redraw never shows the char's `TILE_COLORS` colour); it skips while the small search popup is up. `SETUP_EXPLODE` uses `PAINT_WIN` to turn the cell dark grey. It passes through robots and lasers (only player collisions are checked), and a hit on the player is the ordinary sprite collision (`$D01E` bit 0) → `PLAYER_DIE`. `DRAW_ROOM` clears `BOLT_ON` (room change, respawn, every redraw), and `BOLT_TICK` then turns sprite 3 off. No patrol restriction (the shooter never leaves its path). There's no firing sound yet (only one SFX slot).

**Smooth movement (gliding).** Logic stays tile-based (`PLR_X/Y`, `ACT_X/Y` — collisions with walls/doors/lasers/terminals/items are all per tile), but sprites don't jump a whole tile (16×16 px) per step. Each sprite has its own pixel position in `GL_PXL`/`GL_PXH`/`GL_PY` (runtime arrays in `world.asm`, `NUM_ACTORS+1` long: slot = actor index, last slot `GL_PLAYER` = the human), and `GLIDE` (`game.asm`) moves it `GL_SX`/`GL_SY` px per frame toward the pixel position of its tile, clamping so it never overshoots. Speeds are matched to the step periods so a glide finishes just as the next step starts:
- player, and a player-driven robot: one step per `MOVE_PERIOD` = 8 frames, glide `GL_FAST_X/Y` = 2/2 px per frame (16/8) → continuous walking with no stop at each tile
- idling (patrolling/roaming) robots: one step per `ROB_PERIOD` = 16 frames, glide `GL_SLOW_X/Y` = 1/1 px per frame → continuous too
- a rushing robot (`attack: rush`, `ACT_FAST`): one step per `ROB_HALF` = 8 frames, glide `GL_FAST_X/Y`, like the player
- `SNAP_ALL` (called by `DRAW_ROOM` — room change, respawn, redraws after terminal/map/popup) jumps every sprite straight to its tile, so nothing glides across a room change.
If you change a step period, change the matching speeds (tile pitch / period) or the glide will lag behind or stall. Hardware sprite collisions (`$D01E`) use the glided positions, i.e. what's on screen. A robot that drives into a laser finishes its glide into the beam before it is destroyed (see "Lasers can be destroyed by a driven robot").

**Sprite mapping:** `ASSIGN_SPRITES` (called from the end of `DRAW_ROOM`) scans the actor table for actors in `CUR_ROOM` and assigns them to robot slots 0–3 (`SPR_SLOT_ACT`, 4 bytes, `$FF`=empty; `ROBOT_SLOTS` = 4), setting each slot's sprite pointer and colour from the actor's type. A slot's hardware sprite comes from `SLOT_HW` (1, 2, 5, 6 — sprites 3 and 4 are the bolt and the field), with per-slot `SLOT_ORBIT`/`SLOT_ANDBIT` (its `VIC_SPEN`/`VIC_SP_MSB` bit) and `SLOT_REGOFF` (its X/Y register offset from `VIC_SP1X/Y`); `UPDATE_ROBOT_SPRITES` loops `UPD_SLOT` over the 4 slots. `UPDATE_ROBOT_SPRITES` glides and positions both slots every frame; the glide *targets* use the shared `TILE_TO_PIXEL_X` formula (X pixel = `tile*16+20` — the 24 px sprite centred on the 16 px tile — and Y pixel = `tile*16+62` — feet, sprite line 19, on the tile's bottom line; per-slot `VIC_SP_MSB` bit from `GL_PXH`, needed for tiles 15–19 — see the "Extended (9-bit) sprite X" gotcha) and disables the `VIC_SPEN` bit for any slot that is empty, dead, or out of the room. `genworld.py` rejects configs with more than 4 robots in one room (`MAX_ROBOTS_PER_ROOM`).

### Lasers can be destroyed by a driven robot
`LASER_STATE` (one byte per config laser, 0=active 1=destroyed) implements a one-way puzzle mechanic: driving any proxy-controlled robot into an active laser destroys both.
- `LASER_AT` (`game.asm`) is the shared test — carry set if `NEWX/NEWY` is inside an active laser rect of the current room, returning the laser index in `Y`. `TRY_MOVE` (human) and `TRY_ACT` (driven robot) both call it on every attempted move.
- On a robot hit, `TRY_ACT` doesn't destroy it yet: it sets `ACT_ALIVE=2` ("dying") and remembers the laser in `PEND_LSR`. A dying robot ignores input (`MOVE_ACTOR`) and patrol (`TICK_ROBOT` only moves `ACT_ALIVE=1`), and keeps gliding onto the laser tile; once its sprite arrives, `UPD_DYING` (from `UPD_SLOT`) calls `ROBOT_LASER_DEATH`, which sets that actor's `ACT_ALIVE=0` (sprite hidden for good, patrol suspended forever) and that laser's `LASER_STATE=1` (it stops killing the human too), erases the beam from the screen (`ERASE_LASER`, below), flashes the border yellow via `BFLASH`, and resets `PLAYER_MODE=0` (control snaps back to human without waiting for fire).
- **Destroyed lasers disappear from the room art.** The room maps always have every laser drawn in, so `genworld.py` precomputes per laser a patch list (`LASER_ART_n`, via `LASER_ART_LO/HI`): every cell under the laser rect (its tiles' 2×2 chars ±1 char row, to catch the emitters) whose screen code is in `art.laser_tiles` in `titan.yaml`, with its replacement — the char on both sides if they match (so a beam crossing a wall leaves the wall continuous), else `art.floor_tile`. `ERASE_LASER` (Y = laser index) writes those cells + their `TILE_COLORS` colour; it runs from `ROBOT_LASER_DEATH` and at the end of `DRAW_ROOM` for every destroyed laser in `CUR_ROOM` (so room changes / popup / map / terminal redraws keep it erased; `RESET_ROUND` re-arms lasers before redrawing, so a respawn brings the beam back). The build warns if a laser has no `laser_tiles` under it — usually art and config have drifted apart. New laser glyphs in the charset must be added to `laser_tiles`.
- **Beams flicker.** `ANIM_LASER` (`game.asm`, every 8 game frames from `GAME_ALIVE`) XORs the beam glyph (`$81`) and the beam halves of the emitters (`$82` rows 4–7, `$83` rows 0–3) with `LASER_DASH` (`$18`) **in the charset at `CHARSET` (`$3800`)** — the dashes alternate rows, so this swaps their phase and every beam on screen animates at once with no screen writes. If the laser glyphs are redrawn in vchar64, keep that alternating-row pattern (or update `ANIM_LASER`).
- The terminal blocks re-linking to a destroyed robot: its menu row is dark grey and tagged "destroyed", and `TERM_ROBOT` shows `TMSG_DEAD` instead of linking.

### Sprite collision
`CHECK_SPRITE_HIT` reads `VIC_SPCOLL` (`$D01E`) each frame after all three sprites are positioned. Bit 0 (sprite 0 / player) non-zero means the player overlapped any other enabled sprite. The response is the same as a laser death — both call `PLAYER_DIE` (red border, `DEATH_TMR = ZAP_LEN`, `SOUND_ZAP_START`), so there is one death effect. `$D01E` is cleared by the hardware on read — **but nothing reads it during the death pause** (`DO_GAME` skips `CHECK_SPRITE_HIT` while `DEATH_TMR` runs), so the collision of a robot kill stays latched while the two sprites sit overlapped. `RESET_ROUND` therefore turns all sprites off while it redraws, positions them, reads `$D01E` once to discard the stale hit, and only then re-enables the player sprite; without that, every robot kill killed the respawned player again on its first frame (a second flash, and the time penalty charged twice). (With only 2 sprites the old code checked `bits 0-1`; with 3 sprites a robot-vs-robot collision could set bit 1 or 2 without the player involved, so only bit 0 is checked now.)

### Death & Respawn (Impossible Mission style)
Dying (laser or sprite collision, `DEATH_TMR` counting down to 0 in `DO_GAME`) no longer ends the game outright — it costs time and respawns you:
- `APPLY_DEATH_PENALTY` (`game.asm`) subtracts `CFG_PENALTY_M` minutes (`death_penalty_minutes` in `titan.yaml`) from `CLK_H:CLK_M:CLK_S`, clamped at `0:00:00` (borrows an hour into `CLK_M` when `CLK_M` is short; if `CLK_H` is also `0`, clamps straight to zero rather than going negative).
- If the clock is still nonzero after that, it calls `RESET_ROUND` to respawn **in the same room, where it was entered**: `SAVE_ENTRY` (`game.asm`, on `SETUP_GAME` and every door room change in `DENGO`) saves the player's position in `ENT_X/ENT_Y` (`$4B/$4C`) along with the code counts. Only the room you died in is reset — its actors (`ACT_X/Y/TGT/ALIVE` from their start values) and lasers (`LASER_STATE=0`, a beam burnt out there comes back) — so other rooms keep their burnt-out lasers and destroyed robots; `SETUP_GAME` sets `RS_ALL` (`$4D`) =1 so a new game resets every room (`RESET_ROUND` clears it again). `PLAYER_MODE`, the reactor gauge and the room/HUD redraw reset too; the clock keeps the post-penalty value. Gameplay resumes immediately (`GAME_STATE` stays/returns to 1), with a **2-second grace period**: `ADPRESPAWN` sets `GRACE_TMR` (`$5C`) = `GRACE_LEN` (100 frames) after `RESET_ROUND` (which clears it, so a new game has none). While it runs, `SEES_PLAYER` says no (no rush, shot or force field), `CHECK_SPRITE_HIT` ignores robot collisions (it still reads `$D01E` every frame, so nothing stays latched), and `GRACE_TICK` (from `GAME_ALIVE`, before `UPDATE_SPRITE0` so a pit can still hide the sprite) blinks the player sprite 4 frames on / 4 off and shows it for good at the end. Lasers, pits and traps still kill. It counts game frames, so it pauses with the clock in popups/terminal/map.
- If the penalty brings the clock to exactly zero, it goes to `SETUP_GAMEOVER` instead of respawning.
- **Leaving an unfinished room rolls it back too.** `DOOR_ENTER` (`DENGO`) calls `LEAVE_ROOM` (`orders.asm`) just before a door changes `CUR_ROOM`: unless the room's goal is done (`GOAL_DONE`, the same test as the orders line — a room with no goal or no `done:` is never done, so room 4 always rolls back), it runs `RESET_ROOM` (`game.asm`: the room's robots, lasers and crates back to their start; also the per-room part of `RESET_ROUND`) and `RESTORE_CODES` (codes spent on this visit come back, as on a death). So a puzzle left unsolvable (crates in a corner, the needed robot burnt out) can always be tried again; once the goal is done the room keeps whatever state it's in. Found items, opened doors and found codes are kept either way.
- `RESET_ROUND` is also what `SETUP_GAME` calls (after separately setting the starting clock from `CFG_CLK_H/M/S` and hiding all items again — `ITEM_STATE` is inventory and survives respawns, so only `SETUP_GAME` clears it) to avoid duplicating all the per-round init — see the comment there for the shared/not-shared split.
- The game can now also reach Game Over purely by the clock running out with no death in between: `GAME_ALIVE` checks `CLK_H|CLK_M|CLK_S` right after `TICK_CLOCK` every frame.
- `TICK_CLOCK` itself now clamps at `0:00:00` (early-returns if already zero) — without this, decrementing past zero would underflow `CLK_S`/`CLK_M` to 59 while leaving `CLK_H` at 0, i.e. the clock would visibly jump *up* to `0:59:59` instead of staying at zero.

### Popups (search, locked door) — GAME_STATE=6
`src/popup.asm` implements one shared popup overlay used by two features:
- **Searching (items) — hold fire, Impossible Mission style.** `SEARCH_TICK` (`popup.asm`, called from `READ_KEYS` at `RKSEARCHCHK`) starts a search on a *fresh* fire/Space press outside a terminal zone (the terminal check runs first and takes the press) and only in human mode — **like the terminal, search is human-only** — and **only on a searchable tile**: one whose 2×2 chars aren't all `art.floor_tile` (furniture, crates, the POWER box…; bit 2 of `ROOM_WALLS_n`, `+` in the comment pictures, read via `WALL_AT`). On plain floor fire does nothing at all (no box, you keep walking). `genworld.py` fails the build if an item is placed on plain floor. While fire stays held, `SRCH_TMR` counts up and `MOVE_PLAYER` stands still; time and robots keep running, so searching is a risk. At `SRCH_SHOW` (10 frames — long enough to ignore a tap) a small 11×4 box saying "searching ..." appears just above the player's sprite (below it near the top wall; `SPOP_PLACE`). At `SRCH_DONE` (+50 frames) the generated `ITEM_ROOM/X/Y` tables are checked for a still-hidden (`ITEM_STATE=0`) item on the player's exact tile: if found, the small box goes and `SETUP_SEARCH` (item index in `X`) sets `ITEM_STATE=1` and shows the big popup with the item's generated found-message (`ITEM_MSG_*`, from `found_text` in `titan.yaml`); otherwise the box changes to "nothing / here" and stays until fire is released. Every finished search marks the tile searched (bit 3 of its `ROOM_WALLS_n` byte in RAM, via `SRCH_TILE`); searching a marked tile again shows "nothing here" right away at `SRCH_SHOW`, without the "searching" wait. The marks survive deaths; `RESET_WALLS` clears them on a new game. Releasing fire at any point removes the small box. The small box (`SPOP`) saves the 44 screen + 44 colour cells under it in `SP_BUF` (`$0340`, the unused tape buffer) and restores them on close, so the room art — including an erased laser — comes back exactly; `DRAW_ROOM` resets the search (`SRCH_TMR`/`SRCH_ST`) since a full redraw makes the saved cells stale. Adding a search spot = adding an `items:` entry plus a `things:` placement in the config — no code.
- **Locked door.** `DOOR_ENTER` calls `SETUP_DOOR_LOCKED` when the door's `DOOR_KEY` item is still hidden — the door just acts like a wall.
- All of them (with F2's where-am-I and the robot-link popup) funnel into the shared `SHOW_POPUP`, which draws the box/border/hint rows (`DRAW_POPUP_BOX`, its drawing part, also used by the game over screen) (the "press fire" hint in light red — dark grey was hardly readable; the terminal's hint row is light red too) and takes only the message row's address via `PTR`/`PTR+1` (a 40-byte PETSCII string) — a new popup means one more message string and a one-line caller, not touching the drawing code.
- **The popup closes on a fresh Space press, not `GETIN`.** The Space press that opened it is still in the KERNAL keyboard buffer (the raster IRQ's `$EA31` tail runs the KERNAL keyboard scan every frame), so a `GETIN`-based wait closes the popup after one frame. `DO_POPUP` instead polls the CIA matrix directly with edge detection (`POPUP_ST`, `$33`: 0=opening press still held, 1=released/armed, 2=new press seen; closes on that press's release so the closing Space can't leak into `READ_KEYS` either), and drops any buffered keys (`$C6=0`) on close.
- Unlike terminal/map, the popup does **not** `CLEAR_ROOM` first — `SHOW_POPUP` only overwrites rows 8-13 with a small bordered box, so the room art stays visible underneath. `DO_POPUP` erases it on close by calling `DRAW_ROOM` (full redraw) rather than restoring specific rows.
- Time and robot patrol are paused for free, the same way terminal/map already pause them: `DO_GAME` (and hence `TICK_CLOCK`/`TICK_ROBOT`) simply isn't called while `GAME_STATE=6`.
- `ITEM_STATE` is reset only in `SETUP_GAME` (fresh game), not in `RESET_ROUND` — carried items are inventory and survive a death/respawn, unlike the actor/laser state that `RESET_ROUND` does reset.
- `DRAW_STATUS` (row 24) shows the security code counts and the card: `code: a 2 b 0    card: red` (see "Security codes").
- **Where am I (F2).** Room number and the 2-digit tile X/Y of whoever is driven are no longer on the status line; **F2** (shift+F1, hard to hit by accident on a real C64) opens them in the big popup instead (`SETUP_WHERE` patches the digits into `SBOX_MSG_WHERE`, then `SHOW_POPUP`). `READ_KEYS` scans F1 + either shift on the matrix and edge-detects in `F2_PREV` (`$30`), so a held F2 doesn't reopen it after closing. It works in proxy mode too.

## Room Map

The playfield (screen rows 2–23) is a custom-charset top-down map, 22 rows × 40 chars, authored in vchar64 (see `graphics/` and `src/charset.asm`). Positions are in 2×2-char tiles (20×11 per room). Tile colours come from `TILE_COLORS` (indexed by screen code), not a hand-written switch.

Interior walls are derived from the room art at build time (see "Interior walls" above). So are terminals (from `art.terminal_tiles`). Everything else — lasers, doorways, item spots — is **not** detected from tile bytes: their logical positions come from `titan.yaml` (tile coordinates/rectangles), so the art and those config coordinates can silently drift out of visual sync; check new room art against the config before relying on it. ## HUD Layout (row 0, 40 chars)

```
human     reactor: [########]   00:00:00
^   ^     ^      ^ ^^       ^   ^      ^
0   4    10     17 1920    28  32     39
```
Mode (`human` cyan / `robot NN` green, NN = link seconds left in cols 6–7) on the left, the gauge block centred (`HUD_BAR` = 20, first segment), the clock right-aligned (`HUD_CLK` = 32; white, light red under 10 minutes).
(`#` = one thermometer segment, a solid block `$E0`.)

Row 1 is the **orders line**: `orders:` (yellow) and the current room's goal — white while open, light green with " - done" once achieved. Goals are `goal: {text, done}` per room in `titan.yaml` (text ≤ 25 chars; `done:` is one of `found: <item>` → `ITEM_STATE`≠0, `opened: <room>` → this room's keyed door to that room has `DOOR_OPEN`≠0, `visited: <room>` → `ROOM_SEEN`≠0, `gate: <room>` → that room's gate latched open (`GATE_STATE` = 2, `GOAL_GATE`); no `done:` = never shown done). `genworld.py` emits `GOAL_KIND/ARG` and the padded strings `GOAL_n`/`GOALD_n` (done version) via `GOAL_LO/HI`/`GOALD_LO/HI`. A room with no goal text (room 9) shows an empty row — `DRAW_ORDERS` blanks the `orders:` label too when the goal string starts with a space. `DRAW_ORDERS` (`src/orders.asm`, above `$4000`) redraws the row every game frame after `DRAW_STATUS`, so a find, an opened door or a room change shows at once, and marks `CUR_ROOM` in `ROOM_SEEN` (runtime, cleared only by `SETUP_GAME`).

The reactor gauge visualises the countdown (nothing in the game reads it back). `TICK_REACTOR` sets `REACT_TEMP = 99 − M·89/START` every frame, with `M = CLK_H*60+CLK_M` (minutes left) and `START` the starting countdown in minutes — 10% at mission start (one green segment, clearly safe), 99% as the clock runs out, and a death penalty visibly heats it up. To avoid a runtime division it multiplies `M` by `REACT_K = REACT_SPAN*256/START` (`REACT_SPAN` = 89 = 99 − the starting 10%) (an assembly-time constant from `CFG_CLK_H/M`) and takes the high byte; `genworld.py` rejects a `start_time` under one minute. It also re-rolls a 0–3 flicker (`REACT_JIT`) every 8 frames; the shown value is `REACT_TEMP+REACT_JIT` (capped 99). `DRAW_HUD_DYNAMIC` draws it as an 8-segment thermometer in columns 20–27 (no number — the bar is the whole display): solid blocks (`CH_SOLID` = `$E0` — not `$A0`, which is a room tile in the custom charset), `(shown+6)/12` segments lit in their zone colour from `REACT_ZONES` (4 green, 2 yellow, 2 red), the rest dark gray. Note `DEC2` clobbers `TMP`/`TMP2`/`X` — keep anything you need across it on the stack.

## Visual Style

- Tilted top-down oblique 2.5D perspective (similar to *Cadaver* / *The Last Ninja*)
- VIC-II hardware sprite priority flag used for depth: sprite priority flips when the player walks "behind" tall tiles
- Color palette: C64 dark registers (dark grays, muted blues, deep browns) with high-contrast multi-color tiles
- Flip-screen room transitions (no scrolling); screen RAM blasted per transition
- Charset: custom vchar64-authored charset at `$3800` (`$D018 = $1E`); `$0291 = $0E` written at init

## Custom Charset / Screen Art

Room/HUD art is authored with **vchar64** (charset + screen + colour editor). `graphics/` holds the single vchar64 project for all rooms (`titan.vchar64proj`) plus its ASM exports: `titan-charset.s` (charset), `titan-tile-colors.s` (colour per char), `titan-mapNN.s` (one per room, referenced by `vchar64_map:` in `titan.yaml`) and `titan-char-colorsNN.s` (per-cell colours, not used — the game colours by char via `TILE_COLORS`). The old per-room projects are in `graphics.old/`. `src/charset.asm` is generated from the first two by `tools/gencharset.py` and `!source`d from `titanfall.asm` after `map.asm`.

- **Export format: ASM**, not BIN/PRG. Fits the existing convention (sprites/room data are already inline `!byte` literals in source); avoids managing binary blobs, load-header stripping, or Makefile/Exomizer changes for extra files.
- vchar64 labels its ASM export "ACME-compatible" but it isn't: it emits `.byte` (64tass/KickAssembler syntax), which ACME rejects. So no export is `!source`d directly: `gencharset.py` and `genworld.py` parse the `.byte` lines and re-emit them as `!byte` (and check the sizes: 2048 / 256 / 880 bytes). Just re-export from vchar64 and run `make`.
- **Charset lives at `$3800`** (2K-aligned, the top 2K of VIC bank 0, with the sprite block packed directly below it; moved up from `$2000` and then `$2800` as code growth collided with it — see the gotcha below). `$D018 = $1E` selects screen `$0400` / charset `$3800`. A-Z, digits, and the box-drawing glyphs (`G_HORIZ_BAR`, `G_VERT_BAR`, rounded corners, etc.) used by the intro/gameover/win screens keep their default-ROM-charset code points and shapes — only unused graphics-character slots were repurposed for room-art tiles, so those three screens needed no changes.
- **`TILE_COLORS`** (in `src/charset.asm`, right before the `CHARSET` data) is a 256-byte table indexed by screen code, giving the default colour RAM value for each tile. `COL_BYTE` in `game.asm` does a straight `lda (PTR),y : tax : lda TILE_COLORS,x` lookup instead of switching on individual byte values — **`X` is the caller's page counter in `DRMCPG` and must be saved/restored across the call** (`txa:pha` / `pla:tax`), since `COL_BYTE` needs `X` itself to index the table.
- **Room data is raw screen codes, not PETSCII.** The `ROOM_MAP_n` blocks in the generated `world.asm` (converted by `genworld.py` from the `vchar64_map:` files listed in `titan.yaml`, `.byte`→`!byte`) are blitted straight from `(PTR),y` to `(PTR2),y` in `DRAW_ROOM` with no `PET2SCREEN` conversion (the vchar64 export already emits screen codes). Don't add a `PET2SCREEN` call back in if editing this path.
- **Collision is byte-driven only for walls, and only at build time.** `genworld.py` turns the wall chars (`art.solid_tiles`) in each room map into the `ROOM_WALLS_n` tile grid; the game never inspects screen RAM. Terminals are found in the art too (`art.terminal_tiles`, see "New terminal"). Lasers and doorways still come from the `titan.yaml` tables, so the art and those coordinates can silently drift out of visual sync; check new room art against the config rectangles before relying on it.
- Screen/colour canvases are authored at 22 rows in vchar64 (matching the runtime playfield — 2 HUD rows + 1 status row are drawn by game code, not part of the room art).

## Critical Gotchas

### BASIC ROM is banked out — keep it that way
The high area grew past `$A000` (2026-10-10, rooms 10/11's plates/mirrors). With the default `$01` = `$37` the CPU reads the BASIC ROM at `$A000–$BFFF`, not our code: the game jammed (`JAM at $A23B`, inside `GATE_RESET`) as soon as `SETUP_GAME` ran code up there, with no build error. The entry point now writes `$01` = `$36` right after `sei` (BASIC out; KERNAL and I/O stay in — `GETIN`, the `$EA31` IRQ tail and the keyboard scan are KERNAL). The game never calls BASIC. Don't restore `$37`, and remember it when reading memory from outside (the VICE monitor shows RAM there).

### Code growth can silently corrupt TILE_COLORS/CHARSET — watch for ACME warnings
`TILE_COLORS` (256 bytes, in `src/charset.asm`) has no fixed address — it starts wherever the code before it (all of `titanfall.asm` + every `!source`d module) happens to end, and the next segment, the sprite block (`SPRITES_START`, right below the charset pinned at `* = $3800`), is fixed. If code+`TILE_COLORS` ever grows past it, ACME does **not** fail the build — it prints `Warning - ... Segment starts inside another one, overwriting it.` and silently overwrites the tail of `TILE_COLORS` with sprite data (with the old layout the charset came right after it — same symptom). Since most room tiles use screen codes in the `$80s`-`$A0s`, this corrupts colour lookups for most of the room art (tiles render in wrong/black colours) while leaving the charset bitmaps themselves intact — exactly the "graphics look horrible, wrong colours" symptom, with no build error to point at it.
- **Always check `make`'s full output for `Warning` lines, not just for a nonzero exit code** — a successful build can still have silently corrupted data.
- To check headroom: `acme -f cbm -o /tmp/g.prg -l /tmp/labels.txt src/titanfall.asm` then `grep TILE_COLORS /tmp/labels.txt` — its start address + 256 must stay under `SPRITES_START`. **As of 2026-10-10 (end of content work) `TILE_COLORS` starts at `$1D1F` (ends `$1E1E`) and `SPRITES_START` is `$2700` (the cut scene's 4 frames), leaving ~2.2 KB** (after moving the CPU-only modules above `$4000`). Every sprite frame added costs 64 bytes of that. Unrolled 40-byte row-copy loops are the usual bloat: prefer a `DRAW_ROWS` table (see "Screen Art") for new screens.
- Keep *data* out of the code area where possible: the intro logo, sprites and all generated world data already live outside the code area (sprites below the charset, logo and world data from `$4000`); prefer `$4000+` for new tables/strings too.
- `CHARSET` was moved `$2000` → `$2800` → `$3800` for exactly this reason. `$3800` is the top of VIC bank 0, so **the charset can't move any higher**. Sprites can't go above it either: sprite pointers are 8 bits (`address/64`), so every frame must be below `$4000`. That's why the sprite block is packed *below* the charset — a sprite block at `$3800+` only holds 32 frames. The CPU-only modules (`intro`, `gameover`, `win`, `terminal`, `map`, `popup`) have already been moved above `$4000`, after the world data. If the code area fills up again: put new non-time-critical code in a module up there too (just `!source` it after `popup.asm` — modules must end in `rts`/`jmp`/data, never fall through into the next), move parts of `game.asm` up as well (only the VIC data — charset, sprites — has to stay below `$4000`; code can live anywhere below `$C000`), or switch the VIC to another bank (screen, charset and sprites all move — a much bigger change). If the charset ever moves, update `VIC_VMCSB` in `titanfall.asm` (`$D018 = (screen_base/1024)*16 + (charset_base/2048)*2`; `$0400`/`$3800` → `$1E`).

### CLS wipes the sprite pointers
`CLS` clears all 1024 bytes of screen RAM (`$0400–$07FF`), which includes the sprite pointer table at `$07F8–$07FF`. After **every** `CLS` call, immediately restore all three pointers:
```asm
jsr CLS
lda #SPRP_PLAYER : sta SPRPTR
lda #SPRP_ROBOT  : sta SPRPTR+1
lda #SPRP_DRONE  : sta SPRPTR+2
```
(`ASSIGN_SPRITES` re-points the robot sprites 1, 2, 5, 6 per room afterwards, but the defaults keep the table sane in non-game states.) `CLEAR_ROOM` (which clears only rows 2–23, `$0450–$07BF`) does **not** reach `$07F8` and does not need a restore.

### CIA1's Timer A IRQ must be disabled before installing the raster IRQ
`$0314`/`$0315` is the general IRQ vector — it fires for **any** IRQ source, not just the VIC raster compare. The KERNAL leaves CIA1 Timer A (the jiffy clock) running at ~60Hz from boot. `RASTER_IRQ` doesn't check which source triggered it, so if CIA1's IRQ isn't disabled, the handler runs on both sources combined (~50Hz raster + ~60Hz CIA ≈ 110Hz) instead of just 50Hz — this manifested as music and the countdown clock both running at ~2x speed. Fixed by disabling CIA1's IRQ sources during init, before `cli`:
```asm
lda #$7F : sta CIA1_ICR   ; disable all CIA1 IRQ sources
lda CIA1_ICR                ; ack any pending CIA1 IRQ
```
This doesn't break keyboard input — `READ_KEYS` polls the CIA1 matrix registers directly, and `RASTER_IRQ`'s `jmp $EA31` tail only needs to run once per raster tick, not to be triggered by a CIA interrupt.

### Table loops count up, not down
All loops over the generated world tables use the counting-up pattern `ldx #0 : L cpx #NUM_* : bcs done : ... : inx : bne L` rather than `ldx #NUM_*-1 ... bpl`. This is deliberate: a config with zero entries of some kind (no lasers, no items) makes `NUM_*-1` underflow to `$FF` and a `bpl` loop would run 256 times over garbage; the count-up form falls straight through on zero. Keep the pattern when adding new table scans. (The `!fill NUM_*+1` on `ITEM_STATE`/`LASER_STATE` in `world.asm` exists so the label is still a valid address in the empty case.)

### No anonymous or local labels
ACME anonymous labels (`-` and `+`) scope to the entire zone, not the subroutine — with many routines in one file they resolve to wrong targets silently. Local labels (`.foo`) also caused duplicate-definition errors across routines in the same zone. **All labels are explicit global names** (e.g. `CLSP`, `HUDST1`, `TSETB1`).

### Sound effects tick from the raster IRQ
While `SND_TMR > 0`, `RASTER_IRQ` calls `SOUND_TICK` (`game.asm`) *instead of* the music player, every frame and in every game state. (It used to be called from the top of `DO_GAME`, i.e. only in state 1 — an effect still playing when the state changed, e.g. Space straight into the terminal right after the splicer's laser zap, froze with the gate open and blocked the music.) Because it runs inside the IRQ, `SOUND_TICK` may only use `A` (the KERNAL IRQ entry/exit saves A/X/Y) and the `SND_*` variables — never `TMP`/`PTR`/`NEWX` or other main-loop scratch.

### Keyboard matrix — key positions
Convention used throughout `READ_KEYS`: "col N" = CIA1 `$DC00` (PRA) written with bit N cleared (selects that column); "row N" = CIA1 `$DC01` (PRB) bit N, active low (0 = pressed).
```
W (up):            col 1 (PA=$FD), row 1 (PRB bit 1 = mask $02, active low)
A (left):          col 1 (PA=$FD), row 2 (PRB bit 2 = mask $04, active low)
S (down):          col 1 (PA=$FD), row 5 (PRB bit 5 = mask $20, active low)
D (right):         col 2 (PA=$FB), row 2 (PRB bit 2 = mask $04, active low)
Space (search/terminal): col 7 (PA=$7F), row 4 (PRB bit 4 = mask $10, active low)
F1 (F2 = shift+F1): col 0 (PA=$FE), row 4 (PRB bit 4 = mask $10, active low)
F7 (end robot link): col 0 (PA=$FE), row 3 (PRB bit 3 = mask $08, active low)
Left shift:        col 1 (PA=$FD), row 7 (PRB bit 7 = mask $80, active low)
Right shift:       col 6 (PA=$BF), row 4 (PRB bit 4 = mask $10, active low)
```
**The game is fully playable with a joystick in port 2** (move, fire = hold to search / use terminal / select / every "press fire" prompt); the keyboard is an alternative: WASD (not cursor keys), Space, F2 (where am I), F7 (end a robot link early — keyboard only), and in the terminal Return/W/S/F7. There is no map key — the map is a terminal entry. Joystick port 2 works alongside the keyboard: `READ_KEYS` first reads `CIA1_PRA` (`$DC00`) with `PRA=$FF` (no keyboard column selected; bits 0-4 = up/down/left/right/fire, active low) and ORs the directions into the same `KEY_U/D/L/R` flags (held = move). Fire and Space are one button **everywhere**: `MAIN_LOOP` polls port 2 once per frame, reads the Space key from the matrix (col 7, row 4) and ORs it into bit 4 (fire), giving `JOY_PREV` (held bits) and `JOY_NEW` (bits newly pressed this frame, 1=pressed) — so every "fire" in every screen (terminal select, map, intro/game over/win prompts) also takes Space, with the same fresh-press edge detection; `READ_KEYS` ORs held fire (`JOY_PREV` bit 4) with the Space key, then sets `KEY_SPC` = pressed now but not in the previous game frame, `FIRE_PREV` = held now. Actions use the fresh press (`KEY_SPC`) — otherwise fire still held from the terminal's logoff would re-enter the terminal on the next frame — and the search uses the held state. `DRAW_ROOM` sets `FIRE_PREV=1`, so fire held across any screen change (terminal, map, popup, respawn, door) never counts as a new press. (Port 1 would be `$DC01`, which collides with keyboard rows; it isn't read.) The `GETIN`-driven screens also take `JOY_NEW`: fire/Space = "press fire" on intro/game over/win/map (any other key also works — they skip a `GETIN` Space, `$20`, because the KERNAL auto-repeats a held Space into the buffer, which would skip the next screen too), and in the terminal menu fire/Space = select (Return too), up/down = W/S. `SETUP_TERMINAL` and `SETUP_MAP` empty the keyboard buffer (`$C6` = 198 ← 0) on entry; the terminal ignores a buffered Space anyway (only `$88`/`$0D`/W/S are matched). `DO_POPUP` polls fire directly with its own edge detector, alongside Space. Fire/Space does double duty: it enters the terminal inside a terminal zone (`TERMZ_*` tables) and searches anywhere else — items can't be placed in a terminal zone (the build fails), since the terminal check wins (it runs first in `READ_KEYS`). There used to be a dedicated T key for the terminal; it was removed in favor of reusing Space. If a key seems to trigger the wrong action, re-derive its column/row from the matrix table rather than guessing; `col`/`row` values that look adjacent (e.g. row 4 vs row 6) are an easy transcription error.

Terminal menu keyboard navigation: Space selects (as fire, via `JOY_NEW`, a fresh press — the Space that opened the terminal is still held, and doesn't count); `GETIN` (KERNAL keyboard buffer) handles the rest by PETSCII code: `$57`=W (up), `$53`=S (down) — the same keys as WASD in the game; the cursor keys are not used — `$0D`=Return (select), `$88`=F7 (leave).

### Explosion: screen shake with the fine-scroll registers
`DO_EXPLODE` shakes the whole screen (HUD included) by writing random values (from `LFSR_ST`, ANDed with an amplitude that dies away with `EXPL_TMR`) into the fine-scroll bits 0–2 of `$D011` (vertical) and `$D016` (horizontal) every frame; `SETUP_EXPLODE` saves both and `EXDONE` restores them before `SETUP_WIN`. Sprites don't move with the scroll registers (the player/robot stay put while the room shakes — acceptable for 2 s). **`$D011` bit 7 reads back as bit 8 of the *current* raster line** but is bit 8 of the raster *compare* on write — so every read-modify-write of `$D011` must clear it (`and #$78` / `and #$7F`), or the raster IRQ moves from line 50 to line 306.

### Sector map
Generated entirely by `genworld.py` (`build_map`) from the doors — nothing is hand-drawn. Each door's rectangle says which wall it's on (`door_dir`: left/right/up/down — it must lie outside the room), so starting from the start room every door places the room it leads to in the neighbouring grid cell; the build **fails** if two doors disagree about where a room is, two rooms land on one cell, a room isn't reachable through doors, an exit faces another room, or the layout doesn't fit the 22×40 map screen. Each room is a 4-row box (rounded corners, `label:` from `titan.yaml`, default the room's name; up to 12 wide, narrowed to fit), connected rooms get a cyan corridor (two lines between the boxes, the walls turning into it), and every `leads_to: exit` door gets an opening in that wall plus a white stub and "exit" label outside it. Title and prompt are centred above/below. When the grid doesn't fit, `build_map` narrows the boxes (to the longest label + 2), then the horizontal corridors (to 2), then the vertical ones (to 1 row) and the blank rows around the grid. With today's 4×4 grid (8 rooms) that means **map labels can be at most 6 chars** (hence `silo`/`entry`/`vault`). **Capacity (2026-10-10):** the map fits at most a 4×4 grid of boxes (a 5th column only with labels ≤ 4 chars; no 5th row), and the 11 rooms already span 4×4 — new rooms must go into the 5 empty cells of that box. Memory: a room costs ≈ 1.2 KB in the high area (880 map + 220 walls + 64 goal text + table entries); `HIGH_END` is `$A65F` (2026-10-10, 11 rooms + plates/mirrors), ≈ 6.4 KB below `$C000`, so ~5 more rooms by memory — the map is the tighter limit. Keyed doors: at most 15 in all (4-bit keyed-door number in the wall grid; 3 today), anywhere in the file. The result is emitted as `MAP_SCR` (screen codes) and `MAP_COL` (colours) for screen rows 2–23, with an ASCII picture of the map in the comments of `world.asm`; `SETUP_MAP` just copies both and paints the current room's box light green from `MAPHL_*` (also generated from the layout). The old `map_view:` room key is rejected.

### Security codes
Linking a robot at a terminal costs a security code. `titan.yaml`'s `security_codes:` lists the code types — one letter each, at most 3 — with the count the player starts with (0–9): `a: 2`, `b: 0`. Every robot **must** say which code its link costs (`code: a` / `b` / `none`; the build fails otherwise). Generated by `genworld.py`: `NUM_CODES`, `CODE_START`, `ACT_CODE` (code index + 1, 0 = none), `ITEM_CODE` (same, 0 = an ordinary item), the refusal messages `CODE_MSG_n` (`CODE_MSG_LO/HI`), and the whole status-line template `STAT_TMPL` with `STAT_CNT_COL` (9, code 0's digit; codes 4 columns apart) and `STAT_LBL_COL` (the card label); runtime `CODE_CNT` (per code, 0–9) and `CODE_ENT` (its value on entering the current room).
- `SETUP_GAME` copies `CODE_START` into `CODE_CNT`. Codes are inventory, but **a death gives back the codes spent in the room you died in**: `SAVE_ENTRY` (`game.asm`) copies `CODE_CNT` into the runtime `CODE_ENT` on entering a room — `SETUP_GAME` (the start room) and every door room change (`DENGO`) — and a respawn (`APPLY_DEATH_PENALTY`, `ADPRESPAWN`) copies `CODE_ENT` back. Leaving a room whose goal is done keeps them spent (codes spent in finished rooms stay spent), leaving one whose goal isn't done gives them back (`LEAVE_ROOM`, see "Death & Respawn"); a failed attempt costs time, not codes. A code *found* in the room is added to `CODE_ENT` as well (`SETUP_SEARCH`), since its item stays found after a death. The respawn (same room, at the entry point) keeps `CODE_ENT` as it is (those are the counts it's entered with).
- `TERM_LINK` (`terminal.asm`) checks dead → locked → code. With `CODE_CNT` = 0 it refuses with the code's message on the terminal's message row (row 18, `TERM_MSGROW`, light red, like locked/destroyed); otherwise it decrements the count and starts the link.
- An item with `code: <letter>` is a findable code: `SETUP_SEARCH` adds one to `CODE_CNT` (capped at 9 — one digit) besides marking it found. A code item can't be a door `key:` (build error).
- `DRAW_STATUS`: the counts in yellow over the template, then after `card:` the label of the first *carried* item that isn't a code (`ITEM_STATE`=1 — a used-up key, 2, isn't shown — and `ITEM_CODE`=0), light red.
- Current config: start with 2 × A, 0 × B; the dozer (room 1), drone (room 2) and tripod (room 3) cost A; the room-1 sentry costs B (but is also `locked: true`) and the room-4 guard costs B; the room-5 sentry costs A (moot: room 5 has no terminal); room 6's tripod, room 7's, room 10's and room 11's dozers cost A — 4 A codes are needed for the main route plus the east/top wing, exactly the 2 at the start + `code_a1` + `code_a2`. Hidden codes: `code_a2` in room 10's cabinet at (1,3); `code_b1` in room 8's cabinet at (1,3) — the way to take over the missile-room guard, so the east wing (rooms 6–8) is part of the main quest — and `code_a1` in room 5's cabinet at (17,2).

### Terminal menu
`SETUP_TERMINAL` builds the menu on entry from the actor tables: one entry per robot in `CUR_ROOM` (rows 8–11, at most 4 per room; text from the generated `ACT_TROW_n` row — `name:` from `titan.yaml`, plus "locked" for `locked: true`, else "code a" etc. for the code the link costs; a destroyed robot gets "destroyed" drawn over cols 28–36), then **view map** (row 13) and **logoff** (row 14) (the box spans rows 4–17). With no robots in the room, row 8 shows "no units in this sector". `TM_ACT`/`TM_ROW` (per entry: actor index or `TM_MAP`/`TM_LOGOFF`, and screen row) and `TERM_N` drive `TERM_DRAW_SEL` (colours, `>` marker) and `TERM_FIRE`. View map `jsr SETUP_MAP`s; leaving the map (`DO_MAP`) calls `SETUP_TERMINAL` again with `TERM_SEL` still on "view map" (`READ_KEYS` zeroes `TERM_SEL` before a fresh entry).

### Sprite data placement
All sprite frames live in one block packed right below `CHARSET` (see "Sprites"), which must stay inside VIC bank 0 (pointers are 8-bit, so below `$4000`) and outside `$1000–$1FFF` (the VIC sees the character ROM there, not RAM). No runtime copy loop. Pointers are `address/64` — always computed from labels, never hard-coded.

### Sprite collision register clears on read
`VIC_SPCOLL` (`$D01E`) is cleared by the hardware the moment it is read. Read it exactly once per frame in `CHECK_SPRITE_HIT` and act on the value immediately — reading it again will always return 0.

### Extended (9-bit) sprite X
Sprite X is 9 bits: `X pixel = tile*16+20` exceeds 255 for tiles 15–19, and then the slot's `VIC_SP_MSB` bit must be set or the sprite wraps to the left side of the screen. `TILE_TO_PIXEL_X` (`game.asm`) returns the low byte in A and bit 8 in carry; it computes `(tile*8+10)*2` so the only possible overflow is the final `asl`, which lands straight in carry (an earlier 24 px/tile version computed two adds and lost the first add's overflow — keep any future change to the formula to a single overflow point). `GL_TARGET` stores the carry in `GLT_H`, which ends up in `GL_PXH`.

## SID / Music

### Background music
**Our own tune, *Countdown*** (`music/titan_theme.asm`, assembled on its own into `music/titan_theme.prg` and packed at `$C000` by exomizer; `MUSIC_INIT`/`MUSIC_PLAY` at the top of `titanfall.asm`): a small 3-voice player plus song data, both in that file (format documented in its header). D minor, 125 BPM (6 frames per row): 4 bars of bass and snare (the title screen), then a 24-bar loop: arpeggio chords + a bell motif, the theme on a pulse lead with vibrato, a bridge. Voice 1 lead/bell (the sound effects' voice), voice 2 bass with the snare interleaved, voice 3 chord arpeggios. Init `jsr $C000`, play `jsr $C003`. The player saves/restores the only zero page it uses (`$FB/$FC`), rewrites freq/pulse/waveform and `$D418` every frame and AD/SR every note (so it recovers after an effect took voice 1), and hard-restarts every note. To audition it outside the game, `make sid` builds `music/titan_theme.sid` (`music/titan_theme_sid.asm`: a PSID v2 header — title/author/released strings live there — plus `!binary` of the PRG, assembled with `acme -f plain`; not committed) for `sidplayfp`/`vsid`. (The game used to play David Whittaker's *Licence to Kill*; it was replaced so the game ships only its own music.)
- Init is called once during startup (after SID clear, before `cli`), play from `RASTER_IRQ` every frame (50 Hz PAL).
- **Game over is silent**: `SETUP_GAMEOVER` sets `MUSIC_OFF` (`$5D`) and gates all three voices off, so `RASTER_IRQ` skips `MUSIC_PLAY` through the missile launch (its rumble is a sound effect, which still plays) and the game over popup. Leaving it for the intro (`GO_GO`) calls `MUSIC_INIT` — the theme restarts from the top — and only then clears `MUSIC_OFF`.
- **Sound effect interlock:** while `SND_TMR > 0`, `RASTER_IRQ` calls `SOUND_TICK` instead of `MUSIC_PLAY`, giving the effect (the laser zap) exclusive SID control. Music resumes automatically when `SND_TMR` reaches 0.
- **Editing the tune:** tempo is fixed at 6 frames per row (`RE_DUR` computes rows×6); instruments (`INS_*`), the wave table (`WT_WAVE`/`WT_NOTE`, loop targets are entry indexes — keep them in step when inserting entries), patterns (`PT_*`, each listed in `PAT_LO/HI` with a `P_*` number) and the three order lists (`ORD1–3`, all voices must stay the same number of bars) are plain data in `titan_theme.asm`. Note lengths max 42 rows (frames must fit a byte). Vibrato assumes notes below ~C7. Play-test after edits with `make sid` + `sidplayfp`.

### $D418 (master volume) discipline
The player writes `$D418` every frame (an earlier third-party player set it only at init — the original reason for this rule). But while `SND_TMR > 0` the play routine is not called, so nothing restores volume during the death-sound window:

**Rule:** never leave `$D418` at `$00`. `SOUND_ZAP_START` sets `$D418 = $0F` (the zap fades through `$D418` but never reaches 0), and `SNDOFF` restores `$0F` after gating off voice 1. `SETUP_GAMEOVER` and `SETUP_WIN` must not write to `$D418` (the win screen keeps the music; game over silences it with `MUSIC_OFF`, not the volume). `SND_TMR` is zeroed explicitly in the init before `cli` — the KERNAL may leave `$1E` non-zero, which would permanently block music in intro.

### Sound effects
Voice 1. Two effects, selected by `SND_KIND` (`$45`; `SOUND_TICK` → `ZAP_TICK` or `BOOM_TICK`):
- **Laser zap** (`SOUND_ZAP_START`, `ZAP_LEN` = 40 frames) — the "bzzzt": a thin 12.5% pulse at ~60–90 Hz (mains-hum range, pitch jittered from `LFSR_ST`) alternating every frame with a high noise crackle, a one-frame gate drop every 8 frames for the stutter, fading out through `$D418` over the last 15 frames. Used for every human death (`PLAYER_DIE`: laser in `TRY_MOVE`, robot in `CHECK_SPRITE_HIT`) and when a driven robot burns out a laser (`ROBOT_LASER_DEATH`).
- **Explosion** (`SOUND_BOOM_START`, `BOOM_LEN` = 100 frames, `SND_KIND=1`) — when the power cell is shot: a low noise blast (attack 0, decay 11 ≈ 1.5 s), its pitch falling with the timer into a rumble, and a second blast halfway through (one frame of gate off, then on).
Both set `$D418 = $0F` on start, and `SNDOFF` gates off and restores `$0F` at the end. A new effect = a `SND_KIND` value, a `*_START` that sets it, and a branch in `SNDKIND`.

## Screen Art

The intro uses a PETSCII box design: a bordered panel (rows 12–21 under the logo and author line) drawn by `DRAW_INTRO_SCREEN` (called from `SHOW_INTRO`, the `DO_GAMEOVER` restart path, and the `DO_WIN` restart path). Game over and win have no screen of their own any more: game over launches the missile in the missile room, win stays on the room after the explosion; both end in the shared popup box (`DRAW_POPUP_BOX`, `SBOX_MSG_GAMEOVER` / `SBOX_MSG_WIN`, "press fire").

**Row lists.** `DRAW_ROWS` (`titanfall.asm`, A/Y = list address) draws a screen from a table of `(screen row, colour, string lo, string hi)` entries ended by `$FF` — the terminal (`TERM_ROWS`) and popup (`SBOX_ROWS`) use it instead of one unrolled copy loop per row. `DRAW_ROW` draws a single row (A = row, `PTR` = string, `TMP2` = colour), `PAINT_ROW` recolours the row at `PTR2`, `ROW_PTR` turns a row number into its screen address.

### Shared string labels (each exactly 40 bytes)
- `SCR_BORDER_TOP` — rounded top border (`G_RD_UL` + 38 × `G_HORIZ_BAR` + `G_RD_UR`)
- `SCR_BORDER_BOTTOM` — rounded bottom border (`G_RD_LL` + 38 × `G_HORIZ_BAR` + `G_RD_LR`)
- `SCR_BLANK` — `G_VERT_BAR` + 38 spaces + `G_VERT_BAR` empty interior row
- `ITR_SEP` — `G_VERT_BAR  ==...==  G_VERT_BAR` separator (reused by all three screens)

**All boxes use the PETSCII line glyphs** from `src/petscii.asm` — rounded corners `G_RD_UL/UR/LL/LR`, `G_HORIZ_BAR`, `G_VERT_BAR` — never ASCII `+`, `-`, `|` (those render as plain/odd glyphs). The terminal box reuses `SCR_BORDER_TOP`/`SCR_BORDER_BOTTOM`/`SCR_BLANK`; the popup's narrower box (`SBOX_*`, columns 4–35) builds its border rows with `!fill 30, G_HORIZ_BAR`; `genworld.py` frames the generated `ITEM_MSG_*` rows with `G_VERT_BAR`; the generated sector map uses the same glyphs (as screen codes, `SC_*` in `genworld.py`). After drawing a box, call `FRAME_EDGES` (full width) / `FRAME_EDGES_LR` (columns preset in `FR_L`/`FR_R`) with the frame colour so the `G_VERT_BAR` ends don't inherit each row's text colour.

All string-copy loops call `jsr PET2SCREEN` to convert PETSCII to screen codes before writing to screen RAM. `PET2SCREEN` is defined in `src/titanfall.asm` after `CLS`.
- `ITR_TAG`, `ITR_M1`–`ITR_M3` — intro panel content (the intro has no title row in the box any more — the logo above it replaces it)
- `TXT_PRESS` — the intro's blinking footer prompt


**Intro layout:** `DRAW_INTRO_SCREEN` copies the logo (`TITLE_SCR`/`TITLE_COL`, raw screen codes, no `PET2SCREEN`) into rows 1–8, the unframed author line (`ITR_AUTH`, "by johan berntsson", centred from its own length `ITR_AUTH_LEN`, MGRAY) on row 10, draws the mission box in rows 12–21 (top border, blank, tagline, separator, blank, 3 mission lines, blank, bottom border), and `BLINK_ON`/`BLINK_OFF` blink the prompt on row 23 (`SCRN+920`). The logo's solid block is screen code 224 (`$E0`), not the usual 160 (`$A0`) — `$80–$A2` in the custom charset are room-art tiles, and `$E0` is the other all-ones glyph in the ROM font. Any new full-screen PETSCII art must likewise avoid the room-art codes — `$80–$AA` and more as rooms are added (check `src/charset.asm`).

## Current Status

**2026-10-10: content complete — next phase is balancing and play-testing.** Eleven rooms on the 4×4 sector map, every planned mechanic in: lasers (burnt out by a driven robot), laser traps, pits, pushable crates (filling pits), pressure plates holding a gate open (room 10), a laser emitter steered by pushable mirrors onto a target (room 11), keyed doors, security codes, terminals and robot links, five robot behaviours (patrol/roam × none/rush/shoot/forcefield), up to four robots per room (room 9, the arcade room), death with a time penalty, a respawn grace period, and room roll-back when an unfinished room is left. The main route: entrance (5) → room 2 → room 3 → east wing (6, 7: blue card) → vault (8: code B) → room 9 → room 1 (red card) → room 2's blast door → missile room (4): take over the guard with code B and shoot the power cell. Rooms 10 and 11 (via room 8's left doorway) are a side branch with the two newest puzzles and the placeholder "launch override". The music stops on game over until the intro.


The core puzzle loop is in place and playable end-to-end: start in the entrance (room 5) past its sentry, explore, take over the dozer via the terminal, drive it into the laser (it slides into the beam, the beam vanishes from the art with a "bzzzt"), search for the access card, open room 2's locked door into the missile room, get through the east wing (room 6's laser trap and tripod, room 7's crate puzzle for the blue card, room 6's door) to the B security code in room 8, take over the missile-room guard and shoot the power cell to win — with a real risk/reward death penalty (lose time + respawn where the room was entered) instead of an instant Game Over, and Game Over genuinely tied to the countdown clock hitting zero. As of 2026-10-09 the orders line (row 1) tells the player each room's goal and marks it done, closed doors are solid, and a tile searched once answers "nothing here" at once.

The world is **config-driven**: rooms (bounds, player start, vchar64 map), robots (type, start, patrol waypoints, idle/attack behaviour), items (position, label, found-text), doors (rect, destination, arrival position, key), lasers, the starting clock, the death penalty and the art codes (floor, laser, wall chars) all live in `titan.yaml` and are compiled into `src/world.asm` data tables at build time. Interior walls, terminals and the laser-erase patches are derived from the room art by `genworld.py` (and the sector map from the doors), which also rejects placements inside walls. Adding a room = a vchar64 map export + a `rooms:` entry + its doors; the sector map is generated from the doors. Adding an item, door, laser, robot, security code or robot behaviour (`idle:` `patrol`/`roam` × `attack:` `none`/`rush`/`shoot`/`forcefield`) is config-only. `make release` builds `release/titanfall.d64`.

Presentation (as of 2026-10-07): multicolour animated sprites with 4-way facing (walker player; a sentry and a tracked dozer in room 1, a hovering drone in room 2, a tripod in room 3, a guard robot in room 4), smooth gliding movement between tiles, a PETSCII block-letter title logo + author line on the intro, rounded PETSCII frames with uniform frame colours on every box (intro, game over, win, terminal, popups, sector map), a working reactor thermometer tied to the countdown, a flickering cyan/purple power cell, a 2-second explosion (screen shake via the fine-scroll registers, border fire, explosion sound) as the win payoff, and an original music theme (*Countdown*, 2026-10-08; replaced the third-party tune — awaiting play-test feedback). The obvious visual glitches (robots over the terminal, wrong spawn in room 2, walking through walls, blank reactor HUD, terminal cursor on several rows) are fixed.

Controls and interface (as of 2026-10-07; tested on a real C64 with a joystick): the game is fully joystick-driven, and WASD + Space work exactly like the joystick + fire everywhere (Space is merged into fire in `MAIN_LOOP`; W/S also move in the terminal menu). F2 shows room and position. Fire opens a terminal (any console in the art), selects in menus, and — held — searches, Impossible Mission style (small "searching" / "nothing here" box by the player, the big popup on a find; time and robots keep running). The terminal menu lists the robots in the current room (generated, with `locked:`/destroyed states), then "view map" and "logoff"; there is no map key. HUD: mode left (with the robot link's seconds left, "robot 30"), reactor gauge centred, clock right. A robot link costs a security code (A/B counts on the bottom line, `card:` shows the carried key or "not found"), lasts 30 seconds (F7 ends it early); a driven shooter robot can fire bolts. A robot catching the player and walking into a laser give the same single death (the player slides onto the beam first); the laser beams flicker via the charset. Everything about positions is on a 2×2-char (16×16 px) tile grid; walls, terminals, the laser-erase patches, the sector map and the charset are all generated at build time from the art and the doors.

## What's Not Yet Implemented

- Robot abilities: every linkable robot drives the same way (any of them would burn out a laser); the per-type capabilities from the design (loader immune to lasers, splicer through ducts, centurion armed) aren't implemented. The room-1 sentry is `locked: true` so the dozer stays the puzzle's key
- Robot behaviour in `titan.yaml` is `idle:` `patrol` (two-waypoint shuttle) or `roam` (random walk over the room) × `attack:` `none`, `rush` (charge along the tile row on sight), `shoot` (fire bolts along the row) or `forcefield` (advance behind a force field). Not all combinations are in use yet (no patrolling rusher, no roaming shooter). Ideas: sight only in the facing direction (sneaking up from behind), vertical line of sight, chasing around corners
- Max 4 robots per room (hardware sprites 1, 2, 5, 6; enforced by `genworld.py`) — a sprite multiplexer is deliberately out of scope. Room 9 (the arcade room) uses all 4
- Room 4's goal ("disable missile") has no `done:` — winning ends the game; room 5's EXIT pushes do nothing (no popup)
- The reactor gauge is display-only — nothing happens when it's in the red (an idea: make it a real hazard)
- Weapons: the bolt (`attack: shoot`, hw sprite 3) and the force field (`attack: forcefield`, hw sprite 4) are in use; sprites 5–6 are robots 3–4, so only sprite 7 is free (a second bolt would fit). A player-driven forcefield robot doesn't raise its field (only a driven shooter can fire)
- Furniture is walk-through (not in `art.solid_tiles`); walls only check the sprite's feet, so the upper body overlaps wall art in the oblique view (intended)
- Every terminal shows the same menu (the current room's robots, map, logoff); there's no per-terminal behaviour yet (e.g. a terminal that only reaches certain robots or unlocks something)
- The code area has ~2.2 KB left before the sprite block (`$2700`), the high area ~6.4 KB below the music (`$C000`); new CPU-only code goes above `$4000` (see the TILE_COLORS and BASIC ROM gotchas)
- Room 11's launch override module is a placeholder goal: finding it has no effect on the rest of the game (an idea: make it required for the win, or have it disarm something)
- The glyphs `$B1`–`$B8` (plate, gate, emitter, horizontal beam, mirror backing and the two diagonals, target) are first-pass placeholders drawn by script into the vchar64 project — to be redrawn
- Room 8 ↔ room 10's doorway is only one tile high in logic (the art's opening is char rows 15–18, tiles start on even rows); room 7's two bottom-left crate stacks are off the tile grid, so they're fixed walls (the build warns)
- Untuned: the starting clock (5:47:33), the 30-minute death penalty, the 30-second robot link and the A-code economy (exactly enough codes, refunded when a room is reset) are first guesses — balancing is the next phase
